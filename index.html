I / Getting Started

Getting Started

This guide covers setting up and using a Windows + Linux dual-boot system on the same computer.

It focuses on the main problems you are likely to run into: preparing the disk, partitioning, installing both operating systems, configuring the boot process, and keeping the finished setup reliable.

It also provides a basic headstart on what to do after first booting into Windows or Linux, including useful configuration and everyday setup.

We will go through preparing the installation media, inspecting and preparing the disk, installing Windows and Linux, configuring the bootloader, and performing some basic first-boot setup.

For a quick general overview, see Dual-booting on Wikipedia.

Scope: This is a practical guide rather than a deep dive into operating systems, filesystems, or bootloader internals. The goal is to give you enough context to understand what you are doing, along with enough instructions to get it done safely.
I.a / The Plan

The Plan

The goal is simple: finish with a computer that can boot both Windows and Linux from the same machine, while keeping the storage layout clean, understandable, and recoverable.

We will work from the disk and firmware level upward. First, we will identify how the computer currently boots and how its storage is arranged. We will then prepare the installation media, deal with partitioning, install the operating systems, configure the boot process, and finally perform some basic setup after the first boot.

The general process

  1. Prepare the required Windows and Linux installation media.
  2. Check the computer's current disk and boot configuration.
  3. Plan the partitions and decide where each operating system will live.
  4. Install Windows and Linux in the appropriate spaces.
  5. Set up and verify the UEFI boot process and bootloader.
  6. Boot into both systems and perform basic post-installation setup.

Different disk scenarios

The exact partitioning steps will depend on the machine. A brand-new device with an empty disk is straightforward, while an existing Windows installation may already contain personal files and partitions that need to be preserved.

New or disposable disk: If the disk contains nothing that needs to be kept, the partition layout can be planned from scratch. This gives us the most freedom and usually makes the installation simpler.

Existing installation: If the computer already contains Windows, applications, or personal data, the existing layout must be inspected before anything is changed. We will identify which partitions can be replaced or resized and which ones must remain untouched.

Preserving existing data changes the approach. Never assume that a partition is safe to delete just because it looks empty or has an unexpected drive letter. Existing disks will be inspected and documented before making partition changes.

Our target

The exact sizes will vary between different computers, but the finished setup will generally look like this: 



            Physical disk
            │
            ├── EFI System Partition
            │
            ├── Windows
            │
            ├── Existing data
            │ ├── Data partition
            │ └── Data partition...i
            │
            └── Linux
            └── Debian / Linux filesystem

The important part is not the exact number of partitions. Windows and Linux will have their own operating-system space, existing data will be protected where required, and the system will use a modern UEFI + GPT boot configuration.

Main objective: Build a dual-boot system without treating every computer as if it starts from the same disk layout. New disks can be configured from scratch; existing disks will be handled around the data that needs to survive.
I.b / Operating Systems

Windows, Linux, and others

Windows and Linux can both be excellent desktop operating systems, but they have different strengths and different ways of doing things. Which one you prefer mostly comes down to the software you need, the hardware you use, and how much control you want over your system.

For this guide, we are not trying to decide which operating system is "better." The point of a dual-boot setup is that you can keep both and use each one where it makes the most sense.

Windows

Windows is Microsoft's proprietary, closed-source desktop operating system. It has broad hardware, commercial software, and gaming support, and is still the easiest choice when something specifically requires Windows. You can learn more about Windows through Microsoft's official Windows site.

Its strengths include compatibility, gaming support, and a huge commercial software ecosystem. Most PC hardware manufacturers provide Windows drivers and support, and many commercial applications are developed with Windows as a primary target.

The trade-off is that Windows gives the user less control over the underlying system than a typical Linux installation. It is also a proprietary platform, with increasing integration of telemetry, advertising, online accounts, and other platform services. Whether those are deal-breakers depends on how you use your computer.

Windows is generally required for: games that use kernel-level anti-cheat or other Windows-specific components, Adobe software such as Photoshop and Premiere Pro, and other Windows-specific commercial applications.

Linux

Linux is the name of the open-source kernel at the core of a large family of operating systems. A complete Linux system is normally provided as a distribution, or distro, which combines the Linux kernel with system software, libraries, package management, and applications. The Linux Kernel Archives are the official home of the Linux kernel itself.

There are many distributions, each with its own goals and defaults. Debian, Ubuntu, Fedora, Arch Linux, and Linux Mint are just a few examples. They all use the Linux kernel, but they can differ significantly in how they are configured, maintained, and packaged.

The big advantage is freedom. You can choose the distribution, desktop environment, software, and many other parts of the system itself. Linux can be lightly customized, such as changing the desktop and a few settings, or heavily customized to change how the system is built and managed.

Linux is also common in areas such as servers, software development, system administration, embedded devices, and other technical environments. That does not mean it is only for advanced users, though. A well-configured desktop distribution can be used like any other everyday operating system.

The trade-off is that some commercial software and games still have limited or no Linux support. Hardware compatibility can also vary, and some applications may require alternative software or additional configuration.

Linux is commonly chosen for: programming and development, servers and system administration, open-source software, privacy and customization, and games that work through native Linux support or compatibility layers such as Steam for Linux and Proton.

Why use both?

This is where dual-booting becomes useful. You do not have to choose one operating system for everything. Windows can handle software, games, or hardware that works best there, while Linux can provide a more customizable environment for development, learning, administration, or everyday use.

Both systems can have access to the same physical computer while keeping their operating-system files and installations separate. When the computer starts, the bootloader allows you to choose which system to start.

That separation is one of the main reasons this guide takes the disk layout and boot process seriously. A dual-boot system is not simply two operating systems installed side by side; both need to coexist on the same hardware without interfering with each other.

Other operating systems

Windows and Linux are not the only options. Apple's macOS, FreeBSD, ChromeOS, and various other Unix-like and specialized operating systems are available for different hardware and use cases.

macOS is Apple's desktop operating system and is designed specifically around Mac hardware. FreeBSD is a Unix-like operating system with its own kernel and userland, rather than a Linux distribution. ChromeOS, meanwhile, is Google's operating system designed primarily around Chromebook hardware and a web-focused workflow.

These systems can be useful in their own right, and some can be part of multi-boot setups, but this guide focuses on the common Windows + Linux PC setup.

I.c / Basics

What is dual booting?

Dual booting means having two operating systems installed on the same computer and choosing which one to start when the computer boots.

In this guide, Windows and Linux will be installed separately on the same physical disk. They do not run at the same time. You choose one when the computer starts, and the other remains available for the next boot. 

                            ▼
                        Boot menu
                          ┌──┴──┐
                          ▼     ▼
                        Windows Linux

Dual booting is useful when you want Linux but still need Windows for software, games, or hardware that works better with it. It also lets you run each operating system directly on the computer's hardware rather than running one inside a virtual machine.

What makes it work?

The computer needs a way to find the operating systems when it starts. On modern PCs, this is handled by UEFI, the firmware interface that runs before the operating system. UEFI looks for boot programs stored on an EFI System Partition (ESP).

A bootloader is then used to start an operating system. In a typical Windows + Linux setup, a bootloader such as GRUB can provide a menu where you choose between Linux and Windows. Windows also has its own boot manager, so there can be multiple boot entries involved in the overall process. 

            Computer starts
                  │
                  ▼
                UEFI
                  │
                  ▼
            EFI System Partition
                  │
                  ▼
              Bootloader
               ┌──┴──┐
               ▼     ▼
            Windows Linux

The important part for now is simply this: the operating systems are installed separately, but they share the computer's boot mechanism. The bootloader and UEFI configuration determine which operating system gets started.

Dual boot is not virtualization. With virtualization, one operating system runs another inside a virtual machine. With dual booting, the selected operating system runs directly on the computer's hardware.
I.d / Storage

How disk partitioning works

Before installing two operating systems, you need to understand how the computer's storage is divided. A single physical SSD can be divided into multiple partitions, with each partition used for a different purpose.

A partition is simply a defined section of a disk. Windows may assign it a drive letter such as C:, D:, or E:, while Linux normally refers to partitions using device names such as /dev/nvme0n1p1.

These names can look intimidating at first, but they are just identifiers for particular storage devices and partitions. The exact naming scheme depends on the type of disk and the operating system. 

            One physical SSD
            │
            ├── EFI System Partition
            ├── Windows partition
            ├── Data partition
            └── Linux partition

Partitions and filesystems

A partition is the space; a filesystem is the system used to organize files inside that space. They are related, but they are not the same thing.

Windows commonly uses NTFS, while Linux commonly uses ext4. The EFI System Partition normally uses FAT32 because UEFI firmware is designed to read it.

Not every partition needs to be formatted with a filesystem that you normally use for storing files. For example, the EFI System Partition contains boot files rather than your normal documents and applications.

Term Simple meaning
Disk The physical SSD or hard drive.
Partition A defined section of the physical disk.
Filesystem The system used to organize and store files in a partition.
Unallocated space Disk space that currently belongs to no partition.
ESP The EFI System Partition used to store UEFI boot files.
Never use the drive letter alone to identify a partition. Check the disk number, partition size, filesystem, and other identifying information before deleting, formatting, or resizing anything.

What we need for dual boot

At a high level, we need separate storage for Windows and Linux, plus an EFI System Partition for the UEFI boot files. Existing data partitions can remain in place if they have enough space and are handled correctly.

We also need enough unallocated space for the Linux installation if there is no separate disk available. On an existing Windows installation, this usually means shrinking an existing partition rather than deleting it.

The exact layout will depend on whether the disk is new, already partitioned, or needs space freed for Linux. The actual partitioning steps come later in the guide.

Key idea: Partitioning does not mean splitting the SSD into separate physical drives. It creates separate logical areas on the same physical disk.
I.e / Boot

Bootloaders and the boot process

Before Windows or Linux can start, the computer has to go through a small startup process that happens before the operating system itself is loaded. The computer's firmware initializes the hardware, finds a boot program, and hands control to it. That boot program then starts the operating system.

On modern PCs, this process is normally based on UEFI rather than the older BIOS boot method. UEFI is the firmware interface responsible for initializing the computer and locating an operating system's boot files. The UEFI specifications provide the formal definition of how this works.

UEFI and the EFI System Partition

UEFI can load boot programs from a special partition called the EFI System Partition (ESP). The ESP is normally a small FAT32 partition located on a GPT-formatted disk.

The ESP is not where Windows or Linux itself is installed. Instead, it stores the files needed to begin the boot process. Multiple operating systems can use the same ESP, with each system keeping its own boot files in its own directory. 

            Physical disk
            │
            ├── EFI System Partition (ESP)
            │   ├── Windows boot files
            │   └── Linux boot files
            │
            ├── Windows partition
            │
            └── Linux partition

This is one of the important differences between the operating system itself and the files that start it. The operating system can be stored on one partition while the files needed to start it are stored on the ESP.

What is a bootloader?

A bootloader is a small piece of software whose job is to load or start an operating system. It runs before the operating system and acts as a bridge between the firmware and the system being started.

Windows normally uses Windows Boot Manager. Linux systems can use several different bootloaders, with GRUB being one of the most common. You can read more about GRUB in the GNU GRUB documentation.

A bootloader does not necessarily have to display a menu. If the computer has only one operating system, it can simply start it without asking the user to choose anything. In a dual-boot setup, however, a bootloader such as GRUB can display a menu containing multiple operating systems.

                   │ finds boot entry

                   ▼
               Bootloader
                   │

               ▼        ▼

UEFI boot entries

UEFI does more than simply look for a boot file on the disk. It can keep boot entries in its own firmware settings. Each entry can point to a particular EFI executable, such as Windows Boot Manager or a Linux bootloader.

The firmware also maintains a boot order, which determines which entry it tries first. This is why installing a second operating system can sometimes change what happens when the computer starts: the new installer may create a new boot entry or place it before the existing one.

On Linux, these entries can be inspected with tools such as efibootmgr. On Windows, the Windows Boot Configuration Data (BCD) documentation explains how Windows manages its boot configuration.

Where does GPT fit in?

GPT, or GUID Partition Table, is a partitioning scheme used to describe how partitions are arranged on a disk. It is not a bootloader and it does not start the operating system itself.

On modern UEFI systems, GPT is the standard partitioning scheme used for most system disks. This guide therefore aims to keep the Windows and Linux installations in a consistent UEFI + GPT configuration.

Keeping the firmware mode and partitioning scheme consistent is important. Problems can occur when one operating system is installed in UEFI mode while another is installed using an older legacy/BIOS boot method.

What can go wrong?

Boot problems can happen at several different points in this process. Boot files may be missing or damaged, a UEFI boot entry may disappear, the firmware may select the wrong boot entry, or an operating system installer may change the boot configuration.

Problems can also come from mixing boot modes. For example, if Windows is installed using UEFI while Linux is accidentally installed in legacy BIOS mode, the two systems are no longer using the same boot method. That can make the resulting setup confusing and harder to maintain.

Keep the boot mode consistent. For this guide, Windows and Linux will be installed using UEFI on a GPT-partitioned disk. Avoid booting one installer in legacy/BIOS mode when the existing installation uses UEFI.

Later in the guide, we will inspect the existing firmware and disk configuration before installing anything. After both operating systems are installed, we will also verify the UEFI boot entries, boot order, and the ability to start both systems.

I.f / Safety

Important safety rules

Most of the installation is fairly straightforward. The part that deserves the most attention is modifying the disk. A mistake in partitioning, formatting, or selecting the wrong disk can result in data loss, so take a few precautions before making any changes.

Back up important data

Keep an independent backup of anything you cannot afford to lose. A second partition on the same SSD is not a backup because both partitions still depend on the same physical disk. If that disk fails, is corrupted, or is accidentally erased, the data on both partitions can be affected.

Ideally, keep important files on a separate physical device or another reliable backup location. Make sure the backup is actually accessible before starting the installation; having a backup that cannot be restored when you need it does not help much.

If there is no backup, stop. Do not perform partition-table changes, formatting, resizing, or other destructive disk operations until important data exists somewhere else. If you choose to continue without a backup, you are accepting the risk that a mistake or hardware failure could result in permanent data loss.

Identify the correct disk

Never assume that Disk 0, /dev/sda, or /dev/nvme0n1 is the disk you want. Disk numbering and device names can vary between computers and operating systems.

Before using a disk-management tool or command, compare the disk's size, model, partition layout, and other identifying information with what you expect. If you have multiple drives installed, take extra care to distinguish them.

When working from an installer or rescue environment, remember that the device names may not match what you saw in your normal operating system. Always identify the physical disk first, then identify the partition you intend to work with.

Read before you write

Many disk tools allow you to review a change before it is actually applied. Use that opportunity. Check which disk and partition will be affected, what will happen to the existing data, and whether the resulting layout matches your plan.

If a command or installer screen shows something different from what you expected, stop. Do not keep clicking through the installer hoping that the next screen will make things clearer. Go back, inspect the disk again, and make sure you understand what the operation will do before confirming it.

Be careful with destructive commands

Some disk commands do exactly what you tell them to do, even if what you told them to do was a mistake. Commands that delete partitions, format filesystems, overwrite disks, or modify partition tables should therefore be treated as destructive operations.

Do not copy a command from the guide and run it blindly. Understand what the command is targeting and check its output before proceeding. Later sections will explain the commands and tools when they are actually needed.

Golden rule: If you are not completely sure which disk or partition an operation will affect, do not run it. Verify the target, inspect the layout again, or stop and investigate before making the change.
II / Linux Fundamentals

Getting started with Linux

Linux can look unfamiliar if you are coming from Windows, but the basic ideas are not as complicated as they first appear. The biggest difference is that Linux exposes more of the underlying system and gives you more control over how it is configured, managed, and used.

Unlike Windows, where the operating system is generally presented as one complete product, a Linux system is built from several major components. The Linux kernel provides the core connection between software and hardware, while the distribution supplies the rest of the operating system, including system utilities, libraries, package management, configuration, and usually a desktop environment.

The Linux Kernel Archives are the official home of the Linux kernel. You do not normally need to interact with the kernel directly, but understanding its role helps make sense of the rest of the system.

A Linux distribution, or distro, is essentially a collection of these components packaged and maintained together. Different distributions make different choices about software, configuration, package management, release schedules, and defaults. Debian, which we will use in this guide, is one example.

This means that two Linux systems can look and behave quite differently while still sharing the same underlying kernel. One might use KDE Plasma, another GNOME, and another no graphical desktop at all. They are still Linux systems.

This section introduces the terminology you will encounter throughout the rest of the guide. You do not need to memorize everything here. The goal is simply to give you a mental model of what the different pieces are and how they fit together.

The Linux stack

A simplified Linux desktop can be thought of as several layers working together. This is not a strict architectural diagram, but it is a useful way to understand what each component is responsible for.

At the top are your applications: web browsers, text editors, games, development tools, media players, and everything else you actually use.

The desktop environment provides the graphical experience around those applications. It includes things such as the desktop, panels, menus, settings applications, file manager, and other components that make the system feel like a complete desktop. This guide uses KDE Plasma, which is covered in more detail later. The official KDE Plasma page is a good reference if you want to explore it further.

Underneath the desktop is the display and window system. Modern Linux desktops commonly use Wayland, while X11 (often simply called X) is the older system that is still supported by many setups. These systems handle communication between graphical applications, the display, input devices, and other parts of the graphical session.

The Wayland project and the X.Org project provide more technical information about these two graphical systems. You do not need to understand either one in depth to use Linux, but the names will appear when troubleshooting graphics or desktop sessions.

Below the graphical environment are system services and utilities. These handle many of the tasks that keep the system running, such as networking, logging, hardware management, scheduled tasks, and starting background services. You will interact with some of these through the terminal.

The shell is a command interpreter that lets you interact with the system by typing commands. Bash is one of the most common shells, although other shells are available. A shell is not the same thing as a terminal emulator: the terminal provides the window, while the shell is the program running inside it.

Finally, at the bottom is the Linux kernel. It manages important low-level tasks such as CPU scheduling, memory, devices, filesystems, networking, and communication between hardware and software. Applications normally access these capabilities through system interfaces rather than talking to the hardware directly.

How the pieces fit together

You normally do not need to think about every layer while using Linux. When you open a graphical application, for example, the desktop environment and display system handle the graphical side of things, system libraries provide common functionality, and the kernel ultimately communicates with the hardware.

The same thing can happen through the terminal. When you run a command, your shell interprets it, the relevant program performs the requested operation, and the kernel provides access to things such as files, memory, devices, and networking.

This layered approach is useful when troubleshooting. If the desktop itself is missing, the problem is probably different from a broken application. If a command cannot access a disk, the issue might involve permissions, the filesystem, or the device itself. Knowing roughly where each component fits gives you a starting point for finding the problem.

Why does Linux have so many pieces?

One of Linux's defining characteristics is that these components are not all controlled by a single company or shipped as one inseparable product. Different projects and communities develop different parts of the system, while distributions bring those parts together into something that can be installed and used as a complete operating system.

This is also why Linux gives you so many choices. You can change the desktop environment, shell, applications, services, and many other parts of the system without replacing the entire operating system.

That flexibility can be very useful, but it can also make Linux seem more complicated at first. The good news is that you do not need to understand every component before you can use the system. Most of the time, you can learn each part as you encounter it.

Key idea: Linux is not just the kernel. When people casually say "Linux", they usually mean a complete operating system built around the Linux kernel. The distribution, desktop environment, system tools, applications, and other components all work together to make that system usable.
II.a / Distributions

Linux Distributions

A Linux distribution, usually shortened to distro, is a complete operating system built around the Linux kernel.

The kernel by itself is not a convenient desktop operating system. A usable Linux system also needs system utilities, libraries, package management, configuration tools, software repositories, documentation, and usually a graphical environment.

A distribution brings these pieces together into a system that can be installed, updated, and maintained as a coherent operating system. You can think of the distribution as the particular "flavor" of Linux that you choose to use.

Why are there so many distributions?

Linux is open source, which means that different organizations, companies, and communities can build their own systems around the Linux kernel. They can make different choices about software, configuration, package management, release schedules, security policies, and default desktop environments.

This variety is one of Linux's biggest strengths. Different distributions exist because different people have different needs. A server, an everyday desktop, an old laptop, a development workstation, and a computer used to learn Linux do not necessarily need the same defaults or maintenance model.

There is therefore no single "correct" Linux distribution. A distribution that is ideal for one person may simply be inconvenient for another. The useful question is not which distro is the best?, but which one fits what I want to do?

A few examples

Distribution General characteristics
Debian Stable, conservative, highly configurable, and backed by a very large software repository.
Ubuntu Desktop and server focused distribution based on Debian, with a strong hardware and commercial software ecosystem.
Linux Mint Desktop-focused distribution designed to provide a familiar and approachable experience.
Fedora Modern distribution with relatively recent software and close ties to the Red Hat ecosystem.
Arch Linux Minimal, rolling-release distribution that gives the user significant control over what is installed and how the system is configured.

These are only a few examples. They are not different versions of the Linux kernel; they are different ways of building a complete operating system around it.

Different approaches, not different levels

It is tempting to think of distributions as a ladder where one is "beginner", another is "advanced", and another is "expert". That is not really how it works.

Some distributions simply make more decisions for you, while others leave more decisions in your hands. Some prioritize long-term stability, while others prioritize newer software. Some are designed to work out of the box, while others expect you to build your system piece by piece.

None of those approaches is inherently better. They solve different problems and appeal to different users. Even an experienced Linux user might choose a distribution with sensible defaults when they want to get work done instead of configuring everything manually.

Debian and its ecosystem

Debian is the distribution used throughout this guide. It provides a stable and well-documented base while still exposing you to the underlying Linux concepts you will need to understand.

One of Debian's major strengths is its software ecosystem. Its official repositories contain a very large collection of ready-to-install packages, so you can often install software without manually downloading installers from individual websites. The Debian Packages search is useful for browsing what is available.

Debian also sits at the base of a large ecosystem of other distributions. Ubuntu, Linux Mint, and many other systems build on Debian or its packages in various ways. That means learning Debian concepts can also give you useful knowledge that carries over to other systems.

The official Debian documentation is also worth keeping bookmarked. You will not need to read it from beginning to end; it is mainly useful as a reference when you need information about a particular part of the system.

Distribution families

Distributions are often grouped into families according to their package formats, package-management tools, and shared history. This is useful because learning one distribution often makes related distributions easier to understand.

Debian and Ubuntu belong to the Debian family and commonly use APT with .deb packages. Fedora belongs to the RPM family and uses tools such as DNF. Arch uses its own package format and pacman.

These differences are mostly something you learn as you use Linux. You do not need to memorize every package manager before getting started. What matters is recognizing that instructions can depend on the distribution you are using.

Useful habit: When following a Linux tutorial, first check which distribution and version it was written for. If it uses a different package manager or configuration system, look for the equivalent procedure for your system rather than blindly copying the commands.

Arch Linux and the Arch Wiki

Arch Linux takes a more minimal and hands-on approach. The default installation leaves many decisions to the user, allowing you to build the system around exactly what you want.

This makes Arch particularly useful for people who want to understand how their system is assembled and managed. It also means that an Arch installation can require more decisions and manual configuration than distributions that provide more defaults.

One of Arch's most valuable resources is the Arch Wiki. It contains exceptionally detailed documentation covering installation, hardware, networking, filesystems, bootloaders, desktop environments, troubleshooting, and much more.

You will often find the Arch Wiki useful even when you are not running Arch. Much of the underlying Linux information applies more broadly, although commands and distribution-specific instructions should still be checked before using them on Debian.

Going further: Gentoo

Gentoo takes the idea of user control further. Its package-management system can build software from source with options chosen by the user. This gives you a great deal of control over how the system is built, at the cost of more configuration and, in many cases, more time spent managing it.

Gentoo is a good example of why Linux distributions can be so different: instead of hiding the details, it gives you more opportunities to make those decisions yourself. That can be useful when customization and learning are more important than having the quickest possible setup. The Gentoo documentation provides a good introduction to its approach.

The ultimate DIY: Linux From Scratch

At the extreme end of the hands-on approach is Linux From Scratch (LFS). Rather than installing a ready-made distribution, LFS walks you through building a Linux system yourself, including compiling and configuring many of its core components.

LFS is not something you need for a normal desktop installation, and it is certainly not a requirement for being a "real" Linux user. Its value is educational: it lets you see how the individual pieces of a Linux system fit together and gives you an unusually deep understanding of what goes into a working system.

If you are curious about that approach, the Linux From Scratch project provides the complete book and related projects.

So which one should you use?

II.b / Core System

Linux Kernel

The Linux kernel is the core component of a Linux operating system. It manages the computer's hardware and provides the fundamental services that applications and other system software depend on.

The kernel sits between the hardware and the programs running on the computer. You normally do not interact with it directly. Instead, applications and system software communicate with the kernel through defined interfaces, system libraries, and system calls.

The official Linux Kernel Archives are the main source for the Linux kernel itself, including current releases and kernel development information.

What does the kernel do?

Among many other responsibilities, the kernel manages:

  • CPU scheduling — deciding which processes and threads get CPU time.
  • Memory management — managing physical and virtual memory.
  • Hardware devices — communicating with devices through drivers.
  • Storage and filesystems — providing access to disks and filesystem operations.
  • Networking — handling network devices and network protocols.
  • Process isolation and security — keeping processes and users separated from one another.
  • System interfaces — providing controlled ways for user-space software to request privileged operations.

For example, when an application wants to read a file, it cannot simply access the disk hardware itself. It makes a request through the operating system, which eventually reaches the kernel. The kernel checks the request, accesses the appropriate device or filesystem, and returns the result.

Kernel space and user space

Linux separates normal applications from the kernel. Applications normally run in user space, while the kernel operates in the more privileged kernel space.

This separation prevents an ordinary application from freely accessing hardware or modifying memory belonging to the rest of the system. When privileged work is required, the application asks the kernel through controlled interfaces such as system calls.

You will also encounter the term kernel module. Modules allow certain kernel functionality, particularly hardware drivers, to be loaded and unloaded without requiring every component to be permanently built into the kernel.

Simple way to remember it: User-space programs ask the operating system to do things. The kernel is the privileged component that manages the underlying hardware and core system resources.

Kernel versions and builds

The Linux kernel is continuously developed and released in different versions. Distributions choose which versions to provide and may apply their own patches, configuration, and packaging.

This means two computers can both run Linux while using different kernel versions or configurations. The distribution's package manager normally handles kernel updates, so you generally do not need to download and install a kernel manually.

The kernel can also be built and configured for different requirements. Most desktop users will simply use the kernel provided by their distribution, but specialized systems can use different kernel configurations or patches.

For example, systems that need very predictable scheduling can use real-time (RT) kernels, while audio production and other latency-sensitive workloads may benefit from low-latency configurations. Security-focused systems can use hardened kernels with additional protections, while embedded devices often use kernels configured specifically for their hardware and limited resources.

These are not completely different operating systems. They are different ways of configuring or modifying the same Linux kernel to suit a particular workload. For a normal Debian desktop installation, the standard distribution kernel is usually the appropriate choice.

Key idea: The Linux kernel is the privileged core that connects software to the hardware. Different versions, configurations, modules, and specialized builds allow it to serve everything from ordinary desktop computers to real-time systems and embedded devices.
II.c / Command Line

Linux Shell and Terminal Emulators

One of the most noticeable differences for a new Linux user is how useful the command line can be. Linux provides a large collection of command-line tools that allow you to inspect, configure, troubleshoot, and manage almost every part of the system.

You do not need to become a terminal expert to use Linux. Many everyday tasks can be done graphically, especially on a desktop such as KDE Plasma. The terminal becomes particularly useful when you need precise control, want to repeat an operation, or are following technical documentation.

Two terms are often confused: the terminal emulator and the shell. They are related, but they are not the same thing.

Terminal emulator

A terminal emulator is a program that provides a terminal interface. On a graphical Linux desktop, it is usually a normal application with a window where you can interact with a command-line shell.

On KDE Plasma, Konsole is the standard terminal emulator. Other terminal applications can also be installed and used without changing the underlying shell.

Modern terminal emulators can provide more than a simple text window. They can support multiple tabs and panes, different color schemes, Unicode, 24-bit "true color", hyperlinks, mouse interaction, and other terminal features. Some newer emulators also use the GPU to accelerate rendering, which can make displaying large amounts of terminal output smoother.

The exact features depend on the terminal emulator and the programs running inside it. A terminal application may support a particular feature without every command-line program making use of it.

Shell

A shell is the program that interprets the commands you type. It receives your input, determines what you are asking it to do, and launches programs or performs shell operations.

Common shells include Bash, Zsh, and Fish. They can provide different features, syntax, configuration options, and conveniences, but they all serve the same basic purpose: providing an interface for interacting with the system through commands.

Graphical terminals and headless systems

A graphical terminal emulator is only one way to access a shell. Linux systems can also run headless, meaning there is no graphical desktop or monitor attached to the system at all.

Servers, remote machines, and some embedded systems are commonly managed this way. You can connect to a remote Linux system using tools such as SSH and interact with a shell without needing a graphical environment.

This is one reason the command line is so important in Linux: the same basic command-line tools can be used on a full desktop, a remote server, or a minimal system with no graphical interface.

Why use the terminal?

Linux graphical applications can perform many everyday tasks, but the terminal remains extremely useful because commands can be precise, repeatable, scriptable, and easy to document.

Technical guides also commonly use terminal commands because a command communicates an exact operation without depending on a particular graphical interface. A graphical application might change its buttons or menus between versions, while a command can remain recognizable across many installations.

Do not blindly paste commands. A terminal command can have much more power than a normal graphical action. Read the command, understand what it is expected to do, and verify the target before running commands that modify files, packages, users, or disks.

The prompt

A shell normally displays a prompt when it is ready for input. A typical user prompt might look similar to:

The exact appearance varies depending on the shell and its configuration. In this example, user is the username, debian is the hostname, and ~ usually represents the current user's home directory.

The $ commonly indicates that the shell is running as a normal user. A root shell commonly uses # instead. These characters are part of the prompt shown by the shell, not part of the command you should type.

Key idea: The terminal emulator provides the interface, the shell interprets your commands, and the commands themselves perform the work. They are separate pieces that work together, which is why you can change your terminal emulator or shell without replacing Linux itself.
II.d / Filesystems

Filesystems and Linux Directories

Linux uses a filesystem structure that may look quite different if you are coming from Windows. Instead of normally presenting each storage volume as a separate drive letter such as C: or D:, Linux organizes files into a single filesystem hierarchy.

At the top of this hierarchy is the root directory, written as /. Everything in the normal Linux filesystem tree is reached from this starting point, including files stored on other partitions and disks once those filesystems are mounted.

The structure is defined by conventions described by the Filesystem Hierarchy Standard (FHS). Not every Linux system follows it perfectly, but it provides a useful general map of where things normally live.

The root directory

The top of the Linux filesystem hierarchy is the root directory, written as /. It is the starting point for paths on the system.

Mounting

Mounting means attaching a filesystem to a location in the directory hierarchy. Once a filesystem is mounted, its contents become accessible through that directory, which is called its mount point.

Not everything underneath / is stored as ordinary files on an SSD or hard drive. Directories such as /proc, /sys, and /dev expose information or interfaces provided by the kernel and system rather than representing ordinary stored files.

II.e / Software

Software, Packages, and Repositories

Installing software on Linux is often different from downloading an installer from a website and running it. Most Linux software is distributed through the distribution's package management system.

The terminology can seem confusing at first, but the basic idea is simple: software is organized into packages, packages are obtained from repositories, and a package manager handles installing and maintaining them.

What is a package?

A package is a collection of files and information prepared for installation on a particular Linux distribution. It can contain the program itself, libraries, configuration files, documentation, and metadata describing the software.

Package metadata can include information such as the package name, version, architecture, dependencies, and which other packages it conflicts with or replaces.

On Debian and distributions based on it, packages normally use the .deb format.

What is a package manager?

A package manager is the software responsible for managing packages on the system. It can install, remove, upgrade, and query software while keeping track of what is installed.

Package managers also handle relationships between packages, particularly their dependencies. This means you normally do not have to manually find every library an application requires.

Repositories

A repository is a managed source of software packages. Debian maintains official repositories containing a very large collection of software that can be installed using its package-management tools.

Repositories also provide package metadata, allowing the package manager to determine which versions are available and what those packages require. This is different from simply downloading a collection of unrelated installer files from the internet.

APT and Debian

Debian uses APT (Advanced Package Tool) for managing software from configured repositories. APT works with Debian's .deb packages and can resolve dependencies while obtaining packages from the appropriate sources.

Dependencies

A dependency is software that another package requires in order to work. An application might depend on one or more libraries, utilities, or other packages.

When possible, the package manager resolves these relationships automatically and installs the required dependencies along with the software you requested.

II.f / Graphical System

Display Servers, Window Managers, and Desktop Environments

The graphical desktop on Linux is made up of several components working together. This is another area where Linux gives you a lot of choice: the graphical environment is not one inseparable part of the operating system, so different components can be replaced or configured independently.

The terminology can be confusing at first because some of these components overlap in what they do. The simplest way to approach it is to look at the different responsibilities involved in turning applications and input devices into the graphical desktop you see on screen.

X11 and Wayland

X11, also known as the X Window System, is the traditional graphical system used by Linux and other Unix-like operating systems. In a typical X11 desktop, an X server handles communication with display hardware and input devices, while other components such as the window manager and desktop environment build the actual desktop experience on top of it.

Modern Linux desktops increasingly use Wayland. Unlike X11, Wayland is a display protocol rather than a traditional monolithic display server. A Wayland compositor implements the protocol while also handling responsibilities such as compositing windows and coordinating input and display output.

You will often see Wayland described as the modern replacement for X11. That is a useful high-level description, but both systems can still be encountered today. Some applications and older software also continue to use X11 interfaces through compatibility layers such as XWayland.

You do not normally need to manage X11 or Wayland manually during everyday desktop use. However, knowing which system you are using can be useful when troubleshooting graphics, input, screen sharing, remote desktop software, or application compatibility.

Window managers and compositors

A window manager controls how application windows are arranged, moved, resized, focused, and displayed. It can provide anything from a simple floating-window experience to a highly keyboard-driven tiling layout.

On modern Wayland desktops, the window manager is often integrated with a compositor. The compositor is responsible for combining application surfaces into the final image shown on the screen and can provide effects such as transparency, animations, and efficient handling of multiple displays.

On KDE Plasma, KWin performs these window-management and compositing responsibilities. This is why you may see KWin described as both a window manager and a compositor.

Desktop environments

A desktop environment, or DE, is a collection of graphical components designed to provide a complete desktop experience. It normally includes a window manager or compositor, panels, application launchers, settings applications, a file manager, notifications, system utilities, and other desktop services.

Popular Linux desktop environments include KDE Plasma, GNOME, Xfce, and Cinnamon. They can provide very different interfaces while running on the same underlying Linux kernel and distribution.

II.g / Security

Users and Permissions

Linux is designed as a multi-user operating system. This means the system does not treat every program or person as having unlimited access to everything. Files, processes, devices, and other resources are protected by a system of ownership and permissions.

This is one of the most important ideas to understand when using Linux: your user account is not the same thing as the operating system itself. You normally work with limited privileges, and you temporarily request higher privileges only when a task actually requires them.

Users

Your normal Debian account is a regular user account. It owns your personal files and can perform everyday tasks such as running applications, browsing the web, editing documents, and changing settings belonging to your account.

Linux also has a special administrative identity called root. Root has extremely broad privileges and can access and modify most parts of the system, including files and settings that normal users cannot change.

This separation is intentional. If every application automatically had root-level access, a mistake or compromised program could potentially modify critical system files, access other users' data, or damage the operating system.

Ownership and permissions

Files and directories have an owner and a group, along with permissions that determine what different users are allowed to do with them.

Permission Meaning
Read (r) Read the contents of a file, or view the entries inside a directory.
Write (w) Modify a file, or create, remove, or rename entries inside a directory.
Execute (x) Run a program, or enter/traverse a directory when applied to a directory.

These permissions can apply differently to the file's owner, members of its group, and other users. This allows Linux to keep personal files, shared resources, and system files under different levels of control.

                ├── Owner

Sudo and administrative privileges

You normally do not log into the graphical desktop as root. Instead, an authorized regular user can temporarily perform a specific administrative operation using sudo. 

sudo command

For example, installing system software requires administrative privileges: 

sudo apt install package-name

When sudo asks for your password, it is normally asking for the password of your current user account. Nothing may appear on screen while you type it, not even dots or asterisks. This is normal.

The important part is that sudo does not permanently turn your account into root. It gives the command you specify elevated privileges for the operation being performed.

Why this matters

Permissions are a safety boundary. They help prevent an ordinary application from freely changing the entire operating system, and they limit what a compromised application can access when it is running with normal user privileges.

This is particularly useful on a desktop system. A web browser, media player, game, or document editor normally has no reason to modify /etc, replace system binaries, or access another user's private files. Keeping those areas protected reduces the consequences of mistakes and security problems.

Root can break the system. Administrative privileges bypass many of the protections that apply to normal users. Do not add sudo to a command simply because a tutorial tells you to. Understand what the command does, what it will change, and why it needs administrative privileges.

Not every Linux system gives you the same level of access

The traditional Linux model gives the administrator a great deal of control. That is one of Linux's strengths, especially on personal computers, servers, development systems, and other environments where customization matters.

Other systems deliberately restrict this control. An immutable or image-based operating system keeps important parts of the operating system read-only or manages them as a controlled system image. Applications and user data can still be changed normally, while the underlying operating system is updated as a whole.

This approach can make systems easier to update, recover, and keep consistent because applications cannot casually modify the core operating system. The trade-off is less direct control: traditional system administration techniques may not work in exactly the same way.

Android takes a related approach. It is built on the Linux kernel, but normal Android applications do not receive unrestricted root access. The root account exists underneath the system, but it is intentionally hidden from ordinary applications and users. This helps protect the device and other applications from one another.

Neither approach is universally better. More control is useful when you need to customize, repair, experiment with, or deeply administer a system. More restrictions can be useful when reliability, security, and resistance to accidental changes are the priority.

The important distinction

For everyday use, you should normally work as your regular user. Use administrative privileges only for tasks that actually require them, such as installing system packages, changing protected system configuration, or managing certain hardware.

Linux mindset: Having the ability to become root does not mean everything should be done as root. Normal user privileges are a useful safety boundary. Elevate only when the task requires it, and keep the scope of that elevated access as small as practical.

Verification

Downloading the correct filename is not enough to establish that an ISO is trustworthy. Verification lets you check that the file you downloaded matches a trusted reference and has not been corrupted or unexpectedly modified.

Hashes and checksums

A cryptographic hash is a fixed-length value calculated from a file's contents. Even a small change to the file will normally produce a different hash.

This makes a hash useful for comparing your downloaded ISO with a known good value published by the distributor.

Windows

On Windows, you can calculate an ISO's SHA-256 hash from Command Prompt using: 

certutil -hashfile "C:\path\to\Windows.iso" SHA256

Compare the resulting value with a trusted SHA-256 value published by the image's official distributor. For a Microsoft ISO, use Microsoft's published information where available.

A locally calculated hash is not enough. It tells you what the hash of your downloaded file is. You still need a trusted reference value to determine whether it is the expected image.

Debian

Debian publishes checksums and cryptographic signatures for its installation media. These allow you to verify both the contents of the ISO and, when signatures are checked correctly, the authenticity of the published verification data.

Debian — Verifying authenticity of CD/DVD images

On Windows, calculate the ISO's SHA-256 hash with: 

certutil -hashfile "C:\path\to\debian.iso" SHA256

Compare the result with Debian's published checksums. Debian also provides cryptographic signatures, which provide a stronger form of verification when checked against the appropriate trusted key.

On Linux, the same basic SHA-256 check can be performed with: 

sha256sum debian.iso
Continue only after verification. The filename and file size are useful sanity checks, but the cryptographic hash gives you a much stronger way to confirm that the downloaded file matches the expected image.

VII / Inspection

Inspecting the machine

Before changing anything on the internal disk, we first need to understand the computer we are working with. This means identifying the hardware, checking how the firmware starts the system, inspecting the disks and partitions, and determining which installation scenario applies.

The purpose of this stage is information gathering, not modification. We are not going to delete, format, resize or convert anything yet. First we need to know what is present and what needs to be preserved.

We will also check the computer's processor architecture and other hardware details. This matters because installation images and software are built for particular architectures, and choosing the wrong one can prevent an operating system from booting or installing correctly.

For the disk and boot configuration, the target for this guide is a modern UEFI system using a GPT partition table. We will verify whether the computer already matches this setup before making any changes.

What we will inspect

  1. System information, processor architecture and firmware mode.
  2. Hardware health and basic diagnostics.
  3. Physical disks, partitions and existing data.
  4. Which disk scenario applies to this computer.
  5. Whether an MBR-to-GPT conversion is necessary.
  6. Whether important data is backed up before making changes.
Basic workflow: Inspect the machine → identify the hardware and disk → understand the existing layout → determine the scenario → protect the data → prepare the disk.
Do not skip inspection. Two computers can look almost identical while having completely different partition layouts, firmware settings or hardware. Never apply a partitioning procedure simply because it worked on another machine.
VII.a / System Architecture

Knowing your CPU architecture

Before downloading an operating system or software, it is useful to know which CPU architecture your computer uses. An architecture defines the instruction set and general platform that software is built to run on.

For a typical modern PC, the architecture you will encounter is x86-64, also commonly called amd64. Despite the name, amd64 is not limited to AMD processors; both modern AMD and Intel desktop and laptop processors use this 64-bit architecture.

Common architectures

Architecture Common name Where you may encounter it
x86 32-bit x86 / i386 Older PCs and legacy systems
x86-64 amd64 / x64 Most modern Intel and AMD PCs
ARM64 AArch64 / arm64 Phones, tablets, embedded devices and some modern PCs

You may see different names for the same architecture depending on the operating system or software project. For example, x86-64, amd64 and x64 generally refer to the same 64-bit PC architecture.

Why does this matter?

Operating systems and applications must be compiled for an architecture they can run on. When downloading an ISO, you may therefore see several versions offered, such as amd64 and arm64.

For the standard PC installation in this guide, you will normally want the amd64 version. The important thing is to identify the architecture rather than guessing from the processor's brand or model name.

Checking in Windows

On Windows, open Settings → System → About and look for System type. A modern 64-bit PC will normally report a 64-bit operating system and an x64-based processor.

You can also use Command Prompt: 

echo %PROCESSOR_ARCHITECTURE%

On a typical 64-bit Intel or AMD system, this will report AMD64.

Checking in Linux

Once Linux is available, the uname command can show the architecture of the running system: 

uname -m

A typical 64-bit Intel or AMD PC will return: 

x86_64

ARM64 systems commonly report aarch64.

For this guide: If you are installing Debian on a normal modern Intel or AMD PC, the amd64 installation media is the one you want. The name refers to the architecture, not to the CPU manufacturer.
VII.b / System and Firmware

System and firmware

Before working with the disk, we need to understand how the computer starts Windows. The motherboard's firmware is responsible for initializing the hardware and finding something that can boot an operating system.

Modern PCs normally use UEFI. Older systems may use the legacy BIOS boot method, sometimes exposed as Legacy or CSM in the firmware settings.

For this guide: The final system will use UEFI with a GPT-partitioned disk. We are checking the current configuration first so that we know whether any preparation is necessary.

Check Windows system information

The easiest way to check the current Windows boot mode is with System Information.

Press Win + R, enter: 

msinfo32

In System Summary, find BIOS Mode. It should report either UEFI or Legacy.

BIOS Mode Meaning
UEFI Windows is currently booting using the modern UEFI firmware path.
Legacy Windows is currently booting using the older BIOS/CSM-compatible path.

UEFI normally works with GPT disks and loads boot programs from an EFI System Partition (ESP). The ESP is a small FAT32 partition that stores boot files for operating systems and boot managers.

This means that UEFI boot mode and GPT partitioning are related, but they are not the same thing. The firmware determines how the machine boots, while GPT describes how the disk's partition table is organized.

Check Secure Boot

While still in msinfo32, find Secure Boot State. Secure Boot is a UEFI feature that uses cryptographic signatures to help prevent unauthorized boot software from running before the operating system.

Secure Boot is separate from UEFI itself. A computer can be using UEFI with Secure Boot enabled or disabled.

For the initial installation, we will first concentrate on getting a clean, working UEFI dual-boot configuration. Secure Boot can be configured and verified afterward if required.

Check the Windows version

Run: 

winver

Record the Windows version and edition. You can also check Settings → System → About for additional information, including whether the installed Windows system is 64-bit.

This is useful because the exact Windows version and edition can affect hardware compatibility, encryption features and the installation process.

Check BitLocker and device encryption

Before changing partitions, check whether the Windows installation is protected by BitLocker or another form of device encryption.

Open an elevated Command Prompt and run: 

manage-bde -status

Look for the Windows operating-system volume, normally C:, and check its protection status.

BitLocker provides full-volume encryption for Windows storage. Changes to the disk, firmware or boot configuration can sometimes cause Windows to request the BitLocker recovery key on the next boot.

You can inspect the recovery protectors configured for the Windows volume with: 

manage-bde -protectors -get C:
Know your recovery key first. If BitLocker or device encryption is enabled, make sure the recovery key is safely available before modifying partitions or firmware settings. Do not disable encryption simply because a tutorial says to do so.

Check the firmware settings

The firmware setup screen is provided by the motherboard or laptop manufacturer. The key used to enter it varies between systems; common choices include F2, F10, F12, Del and Esc.

Look for settings related to:

  • UEFI / Legacy boot mode
  • CSM or Compatibility Support Module
  • Secure Boot
  • Boot order

Do not change these settings yet. The purpose of this step is to understand and record the current configuration. We will only change a firmware setting when a later procedure specifically requires it.

What we want to know: Is Windows currently booting through UEFI or Legacy mode? Is Secure Boot enabled? Is BitLocker protecting the Windows installation? These answers will determine which disk-preparation steps are appropriate.
VII.c / Diagnostics

Testing the hardware

Before changing the disk or installing two operating systems, it is worth checking that the hardware is healthy. A dual-boot installation can expose existing problems with storage, memory or CPU stability, so testing first gives us a known-good starting point.

The toolkit uses three main types of tests: SMART for storage health, MemTest86 for system memory, and stress-ng for CPU and general system stability.

Important: These tests are diagnostic tools, not absolute proof that hardware will never fail. A clean result means that the hardware passed the tests performed under the conditions tested.

Storage — smartmontools

smartmontools reads SMART data from supported drives. SMART (Self-Monitoring, Analysis and Reporting Technology) provides information about drive health, temperature, errors and other indicators of storage reliability.

Boot the SystemRescue environment from Ventoy and first identify the drives: 

lsblk -o NAME,SIZE,MODEL,SERIAL,TYPE,FSTYPE,MOUNTPOINTS

For a SATA/SAS drive, run: 

sudo smartctl -a /dev/sdX

For an NVMe drive, run: 

sudo smartctl -a /dev/nvme0

Replace the device name with the actual drive. Never assume that /dev/sda or /dev/nvme0 is the intended SSD.

For a quick overall health check, use: 

sudo smartctl -H /dev/sdX

Look for a result indicating that the SMART health assessment passed. Also inspect the detailed output for media errors, uncorrectable errors, critical warnings and other concerning error counts.

Do not panic over a single temperature or counter. SMART attributes differ between drive manufacturers, and individual attributes can have manufacturer-specific meanings. A failed health assessment, critical warning or significant uncorrectable error should be investigated before continuing.

For NVMe drives, the detailed output normally includes a critical warning field and media/data integrity information. A non-zero critical warning or evidence of uncorrectable media errors deserves investigation before proceeding.

smartmontools documentation

Memory — MemTest86

MemTest86 boots independently of Windows and Linux and tests the system's RAM. This is useful because faulty memory can cause apparently random installation failures, corrupted files, crashes and filesystem damage.

Boot MemTest86 from the Ventoy menu and start the default memory test. Let the test complete at least one full pass. For a machine where reliability is important, several passes or an overnight test provide greater confidence.

The important result is the error count. A healthy test should complete with: 

Errors: 0

Even one reproducible memory error should be treated seriously. If errors appear, shut the machine down and test again after reseating the RAM or testing individual modules, where practical.

If multiple modules are installed, testing them individually can help determine whether the problem follows one particular module. If errors disappear when memory settings are returned to default, an unstable overclock or memory profile may be involved.

Do not continue an OS installation with known memory errors. RAM errors can corrupt data while files are being copied or decompressed, producing installation failures that look like damaged ISOs, bad disks or software problems.

MemTest86 provides the bootable memory-testing software and documentation.

CPU and system stability — stress-ng

stress-ng can place controlled workloads on the CPU, memory and other system components. It is useful for finding instability that may not appear during normal desktop use.

First check the CPU information: 

lscpu

A basic CPU test using all available CPU threads can be started with: 

stress-ng --cpu 0 --timeout 10m --metrics-brief

The test should run without crashes, freezes, kernel errors or reported hardware errors. Watch the system temperature as well; stress testing can produce considerably more heat than normal desktop use.

For a longer stability test: 

stress-ng --cpu 0 --timeout 1h --metrics-brief

Stop the test early if the machine overheats, becomes unstable, freezes or shuts down unexpectedly.

SystemRescue can also be used for a combined CPU and memory workload: 

stress-ng --cpu 0 --vm 2 --vm-bytes 70% --timeout 30m --metrics-brief

This is not a replacement for MemTest86. MemTest86 is specifically designed to detect memory faults, while stress-ng is useful for checking general system stability under load.

Understanding the results

Test Good result Problem result
SMART Healthy assessment with no concerning media, integrity or critical-warning indicators. Failed health assessment, critical warnings, or significant uncorrectable/media errors.
MemTest86 Complete passes with zero errors. Any reproducible memory errors.
stress-ng Test completes without crashes, freezes or hardware errors and temperatures remain acceptable. System instability, kernel errors, overheating, crashes or unexpected shutdowns.
Stop before installation if hardware fails testing. Fix or replace the affected hardware first. Continuing with disk conversion or operating-system installation can make hardware problems much harder to diagnose and can put existing data at risk.
Ready to continue: The target SSD passes its basic health checks, memory testing reports no errors, and the system remains stable under CPU load. The machine can now move on to disk preparation and installation.
VII.d / Storage

Disks and partition layout

Next we need to identify the physical disk that will contain Windows and Linux. This is more important than identifying the Windows drive letter. A drive letter such as C: or D: identifies a Windows volume, not a physical disk.

At this stage we are only inspecting the disk. We are not deleting, formatting, resizing or converting anything yet.

Use DiskPart

Open Command Prompt as Administrator and run: 

diskpart

List the physical disks: 

list disk

Example: 

  Disk ###  Status         Size     Free     Dyn  Gpt
              --------  -------------  -------  -------  ---  ---
              Disk 0    Online          931 GB      0 B        *
              Disk 1    Online          931 GB    931 GB

The Gpt column contains an asterisk when the disk uses GPT. A blank entry means the disk is using MBR.

Do not assume that Disk 0 is the correct disk. Compare the capacity and model with the physical hardware and, where possible, confirm against the information gathered earlier.

List the volumes: 

list volume

Then select the suspected target disk and inspect it: 

select disk N
            detail disk
            list partition

Replace N with the actual disk number. Do not copy an example number without verifying it.

DiskPart has no undo button. Commands such as clean, delete partition and formatting operations can destroy data. Listing and inspecting a disk is safe; modifying it is not.

PowerShell alternative

Windows PowerShell can provide the same information in a convenient tabular form: 

Get-Disk | Format-Table Number,FriendlyName,PartitionStyle,OperationalStatus,Size

To inspect partitions: 

Get-Partition | Format-Table DiskNumber,PartitionNumber,DriveLetter,Type,Size

And filesystems/volumes: 

Get-Volume | Format-Table DriveLetter,FileSystemLabel,FileSystem,HealthStatus,Size

Understand what you are looking at

A physical disk is the actual SSD or HDD. A partition is a region of that disk defined by the partition table. A volume is storage presented to the operating system, normally using a filesystem such as NTFS or FAT32.

Unallocated space is disk space that does not belong to any partition. This is different from unused space inside an existing partition. Debian cannot simply install into unused space inside C:; the required space must first be made available as unallocated disk space or as partitions that can be repurposed.

Common Windows partitions

A typical Windows UEFI installation may contain several partitions that serve different purposes:

  • EFI System Partition (ESP): a small FAT32 partition containing UEFI boot files.
  • Microsoft Reserved Partition (MSR): a small GPT partition used internally by Windows.
  • Windows partition: normally the large NTFS partition containing Windows.
  • Recovery partition: contains Windows recovery tools.
  • Data partition: a partition containing personal files or other data.
  • Unallocated space: space currently available for creating new partitions.

A more detailed explanation of partitions and filesystems is available through Wikipedia's disk partitioning overview.

Graphical inspection

You can also open Windows Disk Management with: 

diskmgmt.msc

Use it as a second view of the disk. Compare the disk number, size, partition order, labels and drive letters with the information collected using DiskPart.

Record the layout. Take a screenshot or write down the disk number, capacity, partition sizes, filesystems, labels and drive letters before making any changes. This record becomes the reference when choosing partitions later.
VII.e / Decision

Determine the disk scenario

Now that the disk and firmware have been inspected, determine which situation applies to the target disk. This decision is important because the correct preparation method depends on whether the disk is empty, already uses GPT, or contains an existing Windows installation using MBR.

Do not change the partition table yet. First identify the scenario, confirm which disk is the target, and make sure any important data is protected.

Scenario 1: New or disposable disk

If the target disk contains no data that needs to be preserved, the simplest approach is to start with a clean GPT partition table and allow the Windows installer to create the partitions required for a UEFI installation.

For a genuinely disposable disk, DiskPart can remove the existing partition information: 

diskpart
            list disk
            select disk N
            detail disk
            clean
            convert gpt
            exit
Destructive operation: clean removes the partition information from the selected disk. The existing partitions and their data will no longer be accessible through the normal filesystem structure. Verify the disk number, model and capacity immediately before running it.

convert gpt then creates a GPT partition table on the now-empty disk. This is appropriate for a disposable disk, but it is not a method for converting an existing Windows installation while preserving its partitions.

Scenario 2: Existing GPT disk

If the target disk already uses GPT, there is normally nothing to convert. Do not erase or recreate the partition table simply because another operating system will be installed.

Next, verify that Windows is actually booting through UEFI. Remember that GPT and UEFI are related, but they are not the same thing: GPT describes the disk's partitioning scheme, while UEFI describes the firmware boot method.

If Windows is already using UEFI and sufficient unallocated space is available, the disk is generally ready for the installation stages. Leave the existing partitions alone unless a later step specifically requires a change.

If the disk is GPT but Windows is still booting in Legacy/CSM mode, stop here. The firmware boot configuration and Windows installation need to be reconciled before continuing with the final dual-boot setup.

Remember: A GPT disk does not automatically mean that Windows is booting through UEFI. Check msinfo32 and confirm the BIOS Mode instead of making assumptions from the partition table alone.

Scenario 3: Existing MBR disk with Windows

If the target disk uses MBR and contains an existing Windows installation or important data, do not use clean. That procedure is intended for disposable disks and would destroy the existing partition layout.

For a supported Windows installation, the preferred approach is Microsoft's MBR2GPT utility. It is designed to convert a Windows system disk from MBR to GPT while preserving the existing partitions and their data, subject to its validation requirements.

MBR2GPT does not simply convert every MBR disk. It first checks whether the current Windows installation and partition layout satisfy the requirements for conversion. The conversion also changes the system from the old BIOS/Legacy boot arrangement to a UEFI-compatible configuration.

If MBR2GPT cannot validate the disk, do not immediately force a conversion. The validation failure normally indicates that the current partition layout or Windows configuration does not meet one of the utility's requirements.

The next section covers MBR-to-GPT conversion in detail, including how to validate the disk, perform the conversion, and handle situations where MBR2GPT cannot proceed normally.

Do not confuse these procedures: clean + convert gpt is a destructive procedure for a disposable disk. MBR2GPT is the preferred approach for converting a supported Windows system disk while preserving its existing partitions and data.

Quick decision guide

Disk situation What to do
Empty or disposable disk Clean the disk and create a GPT partition table.
Existing GPT + Windows using UEFI Keep the existing partition table and prepare available space.
Existing GPT + Windows using Legacy Stop and resolve the UEFI/Legacy boot configuration first.
Existing MBR + Windows/data Use MBR2GPT validation and conversion rather than clean.
The goal: We want to reach a disk using GPT, with Windows booting through UEFI, while preserving any data that needs to be kept. The exact path to reach that state depends on which scenario applies to the machine.
VII.f / Conversion

MBR to GPT conversion

This is the most technical part of disk preparation. The objective is to convert an existing Windows system disk from MBR to GPT while keeping its Windows and data partitions intact.

The preferred approach is to use Microsoft's MBR2GPT utility. It is specifically designed to convert a supported Windows system disk without deleting the existing partitions. Do not use clean and convert gpt for a disk containing data.

Recommended order

  1. Back up important data and obtain the BitLocker recovery key.
  2. Confirm the correct physical disk.
  3. Confirm that the disk is actually MBR.
  4. Check the partition layout.
  5. Run MBR2GPT validation.
  6. Fix any validation problems before conversion.
  7. Run MBR2GPT conversion.
  8. Verify the resulting GPT layout.
  9. Switch firmware from Legacy/CSM to UEFI.
  10. Boot Windows and verify the result.
Do not skip validation. The /validate step checks whether the current disk layout satisfies MBR2GPT's requirements without performing the conversion.

Check the disk first

Start by confirming the physical disk and its partition layout: 

diskpart
            list disk
            select disk N
            detail disk
            list partition
            exit

Replace N with the actual disk number. Confirm the disk's capacity, model and partitions against the information recorded during inspection.

The Gpt column in list disk should be blank for the disk being converted. If it already contains an asterisk, the disk is already GPT and does not need MBR2GPT conversion.

Check BitLocker

Run: 

manage-bde -status

If the Windows volume is protected by BitLocker, make sure its recovery key is available before continuing. A firmware or boot configuration change can cause Windows to request the recovery key.

When required, BitLocker protection can be temporarily suspended with: 

manage-bde -protectors -disable C:

After the conversion and a successful Windows boot, protection can be enabled again: 

manage-bde -protectors -enable C:

If Windows uses a different volume letter in the environment where the command is being run, substitute the appropriate letter.

Keep the recovery key. Suspending BitLocker protection is not the same as deleting or removing BitLocker. The recovery key should remain safely available throughout the entire process.

Validate with MBR2GPT

Open Command Prompt as Administrator and run: 

mbr2gpt /validate /disk:N /allowFullOS

The options mean:

  • /validate checks whether the disk can be converted without performing the conversion.
  • /disk:N specifies the physical disk number.
  • /allowFullOS allows MBR2GPT to run from the normal Windows environment instead of Windows PE.

If validation succeeds, the output should report that validation completed successfully. Do not run /convert if validation fails.

MBR2GPT checks several requirements, including the MBR partition layout, the number and type of partitions, the Windows boot configuration and available space for the EFI System Partition and GPT structures.

Microsoft documents the complete requirements and behavior in the official MBR2GPT reference.

Convert the disk

Only run the conversion after validation succeeds: 

mbr2gpt /convert /disk:N /allowFullOS

MBR2GPT converts the partition table to GPT and creates or reuses an EFI System Partition (ESP). It also installs the required UEFI boot files and updates the Windows boot configuration.

This is the critical conversion step. Do not interrupt the process or restart the computer unless MBR2GPT specifically instructs you to do so. Make sure the backup and recovery information prepared earlier is available before starting.

Verify the result

After MBR2GPT reports that the conversion completed successfully, inspect the disk again: 

diskpart
            list disk
            list partition
            exit

The converted disk should now show an asterisk in the Gpt column. The partition layout should also contain an EFI System Partition.

At this point, Windows may still be configured to start through Legacy/CSM. That is expected if the firmware has not yet been changed.

Switch from Legacy to UEFI

Restart the computer and enter the motherboard or laptop firmware setup. Change the boot configuration from Legacy/CSM to UEFI.

The exact names depend on the manufacturer. Common settings include:

  • Boot Mode: UEFI
  • CSM: Disabled
  • Legacy Boot: Disabled
  • Secure Boot: Leave disabled initially if troubleshooting

Save the changes and boot the internal Windows installation. If the conversion was successful and the firmware is configured correctly, Windows should now start through its UEFI boot entry.

Once Windows has started, run: 

msinfo32

Confirm: 

BIOS Mode: UEFI

Common MBR2GPT failures

A failed validation does not necessarily mean that the disk is damaged. It usually means that the existing partition layout does not satisfy one or more MBR2GPT requirements. The correct response is to identify the specific problem rather than immediately changing or deleting partitions.

Problem What it means What to do
More than three primary partitions MBR2GPT needs room for the GPT/EFI arrangement and cannot automatically handle every four-primary-partition layout. Inspect all partitions first. If one is genuinely unused, removing it may make conversion possible. Otherwise, use careful manual partition planning with GParted or gdisk.
Extended or logical partitions The disk uses the older MBR extended/logical partition structure. Do not randomly delete the extended partition. Identify the logical partitions inside it and determine how their space and data will be handled before making changes.
Insufficient space MBR2GPT cannot find suitable space for the EFI System Partition or GPT-related structures. Inspect the partition layout and available unallocated space. If necessary, shrink an appropriate partition using Disk Management or GParted.
BCD/system partition problem Windows' boot configuration or system partition is not in a layout that MBR2GPT can safely convert. Inspect the Windows boot and system partitions. Repair the Windows boot configuration first if necessary, then run validation again.
Unsupported partition type A partition uses an MBR type that MBR2GPT does not know how to convert automatically. Identify the partition and determine what created it. Do not change its type blindly. Remove it only if its contents and purpose have been confirmed.
Encrypted volume BitLocker protection may require additional handling during the conversion. Make sure the recovery key is available and suspend protection when required.
Multiple disks Windows may have its boot files on a different physical disk from the Windows installation. Identify which disk contains the Windows boot/system partition. Do not convert another disk simply because it contains Windows-related partitions.

MBR2GPT records detailed diagnostic information in its log files. If validation fails, inspect these logs instead of guessing which partition should be changed: 

%windir%\setupact.log
            %windir%\setuperr.log

The built-in help is also available with: 

mbr2gpt /?

If MBR2GPT cannot convert the disk

MBR2GPT should remain the first choice for a supported Windows system disk. If validation fails, correct the underlying layout problem rather than immediately recreating the partition table.

GParted Live is useful when the problem is the physical arrangement of the partitions. It can inspect partitions, create or delete partitions, shrink and expand filesystems, move partitions and create unallocated space.

These operations are performed outside the running Windows installation, making GParted useful when Windows cannot safely modify the required partition.

GParted is a partition editor, not an automatic replacement for MBR2GPT. Use it to correct the layout that prevented MBR2GPT validation, not to blindly recreate the disk.

GParted documentation

Using GParted to prepare the layout

  1. Shut down Windows completely and boot the computer from the GParted Live environment on the Ventoy USB.
  2. Select the correct physical disk. Confirm its capacity and compare it with the disk documented in Windows.
  3. Inspect the complete partition table. Identify the Windows partition, recovery partitions, data partitions and any extended/logical partitions.
  4. Do not modify a partition simply because its purpose is unclear. Identify it first.
  5. If additional unallocated space is required, use Resize/Move on an appropriate partition to create it.
  6. If an unused partition is confirmed to be unnecessary, it can be deleted to create unallocated space.
  7. If an extended partition contains logical partitions, inspect those logical partitions individually before changing or removing the extended container.
  8. Review all queued operations before applying them.
  9. Apply the operations and wait for GParted to finish. Large partition moves can take a long time and must not be interrupted.
  10. Reboot into Windows and allow Windows to perform any requested filesystem checks.
  11. Run MBR2GPT validation again: 
mbr2gpt /validate /disk:N /allowFullOS

If validation succeeds, perform the conversion: 

mbr2gpt /convert /disk:N /allowFullOS
Important: GParted can move and resize partitions, but it cannot guarantee that a Windows installation will remain bootable after every layout change. Never perform a resize or move without a verified backup.

If GParted cannot solve the layout

If the layout is unusual, GParted reports filesystem problems, or MBR2GPT still cannot validate the disk after the layout has been corrected, use the recovery tools on the Ventoy USB. These provide additional ways to inspect and work with the disk outside Windows.

Using SystemRescue

SystemRescue is a bootable Linux recovery environment containing utilities for partitioning, filesystem work, disk inspection and data recovery. It is useful when Windows cannot boot or when a partition operation needs to be performed completely outside Windows.

Boot SystemRescue from the Ventoy menu and identify the disks before doing anything: 

lsblk -o NAME,SIZE,TYPE,FSTYPE,LABEL,MOUNTPOINTS
            sudo fdisk -l

Identify the intended disk by its size, model and partition layout. On a typical system, SATA/SAS disks may appear as /dev/sda, while NVMe disks may appear as /dev/nvme0n1. These names are examples only.

SystemRescue includes GParted for graphical partition management and command-line tools such as fdisk and gdisk for more direct control.

SystemRescue documentation

Using gdisk as the final partition-table fallback

gdisk is useful when the main problem is the partition table itself rather than filesystem resizing. It can read an MBR partition table and construct a GPT representation before anything is written to disk.

From Windows, first identify the physical disk: 

diskpart
            list disk
            exit

Then open the correct physical disk with gdisk: 

gdisk64.exe \\.\PhysicalDriveN

Replace N with the correct physical disk number. Inside gdisk, inspect the current table: 

p

Verify the partition-table structures: 

v

If gdisk has detected an MBR disk, it can prepare a GPT representation without immediately writing it. Carefully review the complete partition list. Partition numbers, starting sectors, ending sectors and sizes should correspond to the layout documented before conversion.

If the proposed conversion is correct and you intentionally want to perform it, write the new GPT: 

w

If anything looks wrong, leave without writing: 

q
Last-resort operation: gdisk is not a safer version of MBR2GPT. It gives you more direct control over the partition table, which also gives you more opportunities to make a disk unbootable or inaccessible. Never write a GPT conversion unless the resulting partition mapping is understood and important data is backed up.

After a successful manual MBR-to-GPT conversion, do not assume that Windows will automatically boot in UEFI mode. The firmware must still be switched from Legacy/CSM to UEFI, and Windows must have a valid EFI System Partition and boot configuration.

If necessary, Windows boot files can be rebuilt from Windows recovery media before continuing with the Debian installation.

Known-good rule: Never solve an MBR2GPT validation error by deleting a partition unless you know exactly what it contains, have a verified backup, and understand how its removal affects Windows boot, recovery and any data stored on the disk.
VII.g / Protection

Backup and data protection

Partition-table changes, resizing and operating-system installation can cause data loss if something goes wrong. Before modifying the disk, make sure anything that must survive the procedure exists somewhere other than the disk being modified.

Back up important data

Copy important files from every partition that must survive the installation to an independent external drive or another reliable storage location.

A second partition on the same SSD is not an independent backup. If the SSD fails, both copies can be lost.

Verify the backup

Do not assume that a completed copy operation means the backup is usable. Open several representative files and confirm that the important folders and data are actually present.

For irreplaceable data, keep more than one independent copy where practical.

Record the original disk layout

Before modifying the disk, save a record of its current structure. From an elevated Windows Command Prompt: 

diskpart


            list disk
            list volume
            select disk N
            detail disk
            list partition
            exit

Replace N with the correct disk number. Also save a screenshot of Windows Disk Management. Record partition sizes, filesystem types, labels and drive letters so that the original layout can be recognized later even if the installer displays it differently.

Protect BitLocker recovery information

If Windows uses BitLocker, make sure the recovery key is available before changing the partition table or firmware settings. A recovery key may be required after hardware, boot or firmware changes. 

manage-bde -status


            manage-bde -protectors -get C:

If MBR2GPT requires protection to be suspended, suspend the protectors before the conversion: 

manage-bde -protectors -disable C:

After Windows has successfully booted through UEFI and the system has been confirmed to be working, protection can be enabled again: 

manage-bde -protectors -enable C:
Keep the recovery key independent. Do not rely on the Windows installation or the disk being modified to provide access to the BitLocker recovery key after a boot or disk problem.

Do not proceed if...

  • The physical disk cannot be positively identified.
  • Important data exists without a verified backup.
  • The recorded partition layout is incomplete or unclear.
  • A partition's purpose is unknown and it is being considered for deletion.
  • You do not have the required BitLocker recovery information.
  • MBR2GPT validation fails and the reason is not understood.
  • The intended UEFI/GPT layout has not been planned.
Ready to continue: The correct disk has been identified, its original layout is documented, important data has an independent verified backup, BitLocker recovery information is available, and the partition layout is understood well enough to safely continue with the Windows installation path.

Booting the Windows installer

VIII.b / Disk

Choosing the disk and creating the partition

Windows Setup displays physical disks and their partitions by number. The numbering used by Setup is not enough to identify the correct drive. Compare the disk size and existing partition layout with the inventory recorded earlier.

Stop if unsure: Never select a disk simply because it is listed as Disk 0. Verify its capacity and existing partitions first. Selecting the wrong disk can destroy another operating system or personal data.

New or completely disposable disk

If the entire target disk is new, empty, or intentionally being erased, Windows Setup can create the required GPT layout automatically.

Remove the existing partitions only after confirming that everything on that disk may be destroyed. The result should be one block of Unallocated Space.

Select the unallocated space and choose New, or select it directly and allow Windows Setup to create its required partitions automatically.

A normal UEFI Windows installation may create several small supporting partitions, including an EFI System Partition, an MSR partition, the main Windows partition, and a recovery partition. These are normal and should not be deleted simply because they are small.

EFI System Partition: The ESP is a small FAT32 partition containing UEFI boot files. It provides the firmware with the files needed to start an operating system. Windows and Debian can use the same ESP for their respective boot files.

Disk already contains data

If the target disk already contains files that must survive, do not delete the existing partitions. Windows Setup is not the place to experiment with an existing partition layout.

The required Windows space should already have been made available during the disk-preparation stage. In the installer, identify the intended unallocated space and select only that space for Windows.

If there is no suitable unallocated space, stop the installation. Do not shrink an unknown partition just to make the installer fit. Return to the disk-preparation stage and determine exactly which partition can safely be reduced.

Using DiskPart when the installer view is unclear

Windows Setup provides DiskPart, a command-line partitioning utility. It is useful for inspecting disks when the graphical installer does not make the layout clear.

Press Shift + F10 in Windows Setup to open Command Prompt, then run: 

diskpart
            list disk
            list volume

list disk shows physical disks and their sizes. list volume shows detected volumes and filesystems. Use these commands to confirm which disk you are working with.

Inspect a particular disk with: 

select disk N
            detail disk
            list partition

Replace N with the actual disk number. Do not guess the number.

Destructive DiskPart commands: Commands such as clean, delete partition, and format modify or destroy data. They are not required for a normal Windows installation onto existing unallocated space.

If the target disk is intentionally being erased and must be converted to GPT manually, the destructive sequence is: 

diskpart
            list disk
            select disk N
            clean
            convert gpt
            exit

After closing Command Prompt, refresh the disk list in Windows Setup. The disk should appear as unallocated space on a GPT disk. Select that space and allow Windows Setup to create its required partitions.

Do not use this sequence on a disk containing data. clean removes the partition information and makes existing volumes inaccessible. This procedure is only for a disk that has explicitly been chosen for complete erasure.

Choosing the Windows partition

Once the correct unallocated space has been identified, select it and start the installation. Windows Setup will normally create the small system partitions it requires and use the remaining space for the Windows installation.

Do not manually create the EFI, MSR, recovery, and Windows partitions unless there is a specific reason to do so. For a standard dual-boot installation, letting Windows establish its normal layout is simpler and easier to troubleshoot.

Completing Windows Setup

First boot, debloating, and basic configuration

Run Windows Update first

Debloating with WinUtil

This guide uses WinUtil, the Windows utility maintained by Chris Titus Tech, for optional cleanup and configuration. It provides Windows tweaks, application installation and system-management options.

The project is available from its official repository.

Understand what debloating means: Debloating changes or removes Windows components, applications, services, or defaults that you may not want. These changes are optional and can affect Windows features, updates, or future troubleshooting. Review each option before applying it.

WinUtil can be started from PowerShell using the command provided by the project's documentation:

This downloads and executes the current launcher from the project's web endpoint. Because it executes remotely downloaded PowerShell code, use only the official project source and review it if you are uncomfortable with this method.

In WinUtil, select only the cleanup and configuration options you actually want. Avoid applying every available tweak without understanding its effect.

Prepare Windows for dual boot

Windows Fast Startup is a hybrid shutdown feature that partially hibernates the Windows kernel instead of performing a completely fresh shutdown. This can leave Windows filesystems in a state that Linux should not modify.

Disable Fast Startup through Control Panel → Hardware and Sound → Power Options → Choose what the power buttons do. Select Change settings that are currently unavailable and disable Turn on fast startup.

Alternatively, an administrator Command Prompt can disable hibernation, which also disables Fast Startup: 

powercfg /h off

If hibernation is intentionally required later, it can be re-enabled with: 

powercfg /h on
Do not modify a hibernated Windows filesystem from Linux. A normal full shutdown is the safe state when switching between Windows and Linux, especially when the Windows partition may be accessed from Debian.

IX.b / Disk

Choosing the disk and creating partitions

Debian's installer can partition the disk automatically, but automatic partitioning is not appropriate when an existing Windows installation must be preserved. Choose manual partitioning so that only the Linux space is modified.

Stop and identify the disk first. Do not select a disk based only on its Linux device name. Compare its capacity and existing partitions with the disk inventory recorded earlier.

Identify the Windows disk

A typical NVMe SSD may appear as: 

/dev/nvme0n1

A SATA drive may appear as: 

/dev/sda

The partitions will normally have names such as /dev/nvme0n1p1 or /dev/sda1. These names are assigned by Linux and may differ between machines.

The Windows partitions should be recognizable by their size, filesystem and position in the partition table. The existing EFI System Partition is normally a small FAT32 partition marked as an EFI System Partition.

Use the existing unallocated space

The preferred layout is to leave the Windows partitions untouched and create Debian partitions only inside the unallocated space prepared earlier.

A simple desktop installation can use:

  • Root (/): the main Debian filesystem. It contains the operating system, applications, system configuration and most installed software.
  • Swap: disk-backed virtual memory used when RAM is under pressure and, when configured appropriately, for hibernation. A swap partition is not strictly required; Debian can also use a swap file.
  • Home (/home): optional separate filesystem containing user files and personal configuration. Keeping it separate can make reinstalling Debian easier, but it is not required for a simple installation.

For this guide, a single Debian / filesystem plus swap is a straightforward choice. A separate /home partition can be used if you specifically want to keep personal files separate from the operating system.

Do not create another EFI partition unnecessarily. The Windows installation already has an EFI System Partition. Debian can use the existing ESP for its UEFI boot files. Select the existing ESP and mount it as /boot/efi; do not format it.

EFI System Partition

The EFI System Partition (ESP) is a small FAT32 partition used by UEFI firmware to locate bootloaders. Windows normally creates one during installation, and Debian can place its GRUB boot files in the same partition.

In the Debian installer, select the existing ESP and set its mount point to: 

/boot/efi

Make sure the format option is disabled. Formatting the ESP can remove existing Windows boot files and make Windows unable to boot until they are repaired.

Creating the Debian root partition

Select the unallocated space and create a new partition for /. For a normal desktop installation, ext4 is the simplest filesystem choice.

Give the root filesystem enough space for Debian, KDE Plasma, applications, updates and personal files if /home is not separate. Leaving additional free space is useful for future growth.

Swap

Swap provides disk-backed memory when physical RAM is insufficient. It can also be used for hibernation, although hibernation requires additional configuration and sufficient swap capacity.

Debian can use a swap partition or a swap file. For a straightforward desktop installation, either is acceptable. Do not feel that a large dedicated swap partition is required simply because the machine has a large amount of RAM.

Partitioning is the irreversible part of the installer. Before applying the changes, review the final partition table carefully. Windows partitions should remain unchanged, the Debian partitions should occupy only the intended free space, and the existing ESP must not be formatted.

Before applying the partition changes

The final layout should resemble this conceptually: 

GPT disk
            ├── EFI System Partition        ← existing Windows ESP, shared with Debian
            ├── Microsoft Reserved          ← Windows
            ├── Windows NTFS                ← Windows
            ├── Windows Recovery            ← Windows
            ├── Debian root (ext4)          ← new
            └── Swap / additional space     ← new or optional

The exact partition order and sizes will depend on the disk and the space reserved during preparation. The important point is that Windows partitions remain intact and Debian is installed only into the space allocated for it.

Ready to install: The correct GPT disk has been identified, the Windows partitions are left intact, the existing EFI System Partition is reused without formatting, and the Debian partitions are being created only in the intended free space.

Restart the machine and verify that GRUB offers both Debian and Windows. Boot Windows once as well to confirm that the existing installation still starts normally.

From Debian, inspect the UEFI boot entries with: 

sudo efibootmgr -v

Look for entries corresponding to Debian/GRUB and Windows Boot Manager. The exact names and boot order depend on the motherboard firmware.

Do not change UEFI entries unnecessarily. efibootmgr -v is being used here for inspection. Do not delete entries or change the boot order unless there is a specific boot problem that needs to be corrected.
Ready to continue: Debian boots through UEFI, KDE Plasma and the basic hardware work, the repositories are configured, Backports is available, and Windows remains bootable from the dual-boot menu.

sudo apt install \

sudo apt update
            sudo apt upgrade

X / Finalizing

Finalizing and Verification

The installation is complete, but the dual-boot setup should be verified before it is considered finished. The goal is to confirm that Windows and Debian both boot correctly, that both use the same UEFI/GPT setup, and that the firmware and bootloader are behaving as expected.

This section also checks a few common post-installation issues, including system time and UEFI boot order.

X.a / Boot

Verify the boot process

Shut the machine down completely and start it again. Confirm that the internal disk boots without the Ventoy USB and that the bootloader provides access to both Windows and Debian.

Boot into Windows, shut it down normally, and then boot Debian. Repeat the test at least once. Testing both directions helps catch problems that may only appear when switching between operating systems.

Confirm UEFI mode

Both systems should be installed and booted using UEFI on the GPT disk. UEFI is the modern firmware interface used to start operating systems and load their boot files from the EFI System Partition.

In Windows, press Win + R and enter: 

msinfo32

In System Information, check BIOS Mode. It should report: 

UEFI

In Debian, run: 

test -d /sys/firmware/efi && echo "UEFI" || echo "Legacy BIOS"

The expected result is: 

UEFI
Do not mix boot modes. Windows and Debian should normally use the same firmware mode. A mixed UEFI/Legacy configuration can work in special cases, but it makes boot management and recovery unnecessarily complicated.

Confirm the EFI System Partition

The EFI System Partition (ESP) is a small FAT32 partition containing UEFI boot files. Windows and Debian can use the same ESP; they do not normally require separate EFI partitions.

From Debian, inspect the partition layout: 

lsblk -o NAME,SIZE,FSTYPE,PARTTYPE,PARTLABEL,MOUNTPOINTS

Look for the small vfat or fat32 partition identified as the EFI System Partition. It should normally be mounted at: 

findmnt /boot/efi

The exact device and partition number depend on the machine. Do not assume that the first partition or first disk is the ESP.

Test the firmware boot menu

Use the motherboard's one-time boot menu to verify that the expected UEFI entries are present. Common keys include F12, F11, F8, Esc, or F2, depending on the manufacturer.

The important result is that the machine can reliably reach both operating systems without the installation USB.

X.b / Time

Fixing the system clock

Windows and Linux can use different conventions for the hardware real-time clock (RTC). Linux normally treats the RTC as UTC, while Windows has traditionally treated it as local time. If the systems use different conventions, the displayed time can change after switching between them.

Check Debian

Run: 

timedatectl

Look for: 

RTC in local TZ: no

This means Debian is treating the hardware clock as UTC, which is the normal Linux configuration. If necessary: 

sudo timedatectl set-local-rtc 0

If Windows continues to display the wrong time after switching systems, Windows can also be configured to interpret the hardware clock as UTC. This requires a registry change and should only be done if the clock actually shows the problem.

If the change is necessary, open regedit and navigate to: 

HKEY_LOCAL_MACHINE\SYSTEM\CurrentControlSet\Control\TimeZoneInformation

Create a DWORD (32-bit) Value named RealTimeIsUniversal and set it to: 

1

Restart Windows and verify the time after switching between both operating systems.

Do not change the clock configuration unnecessarily. If the time remains correct when switching between Windows and Debian, leave the existing configuration alone.
X.c / UEFI

UEFI boot order and recovery

UEFI firmware stores boot entries that point to bootloaders on the EFI System Partition. It also stores a BootOrder that determines which entry the firmware tries first.

Installing or updating an operating system can change this order. If the machine suddenly boots directly into Windows or Debian, the other operating system may still be completely intact; the firmware may simply be selecting a different boot entry.

Inspect the UEFI entries

From Debian, use efibootmgr: 

sudo efibootmgr -v

The output should show the available boot entries and the current BootOrder. Look for entries corresponding to debian or GRUB and Windows Boot Manager.

Do not change the entries simply because their order looks different from an example. Firmware manufacturers label and arrange entries differently.

If one system does not appear

First use the firmware's one-time boot menu. If the missing operating system has its own UEFI entry, boot it directly. This helps determine whether the problem is the operating system itself or simply the normal boot order.

If Windows is missing from GRUB but still boots from the firmware menu, the Windows installation is probably intact and the issue is with GRUB's detected entries. If an entry or boot files are actually missing, repair should be performed only after identifying which part is missing.

Common GRUB caveat: On some Debian installations, Windows may not automatically appear in GRUB because automatic OS detection is disabled or the Windows bootloader is not detected. Do not reinstall either operating system just because the menu entry is missing.
Do not recreate UEFI entries at random. The EFI System Partition, bootloader files, and firmware boot entries are separate parts of the boot process. Identify which part is missing before attempting a repair.
X.d / Checklist

Final checklist

The dual-boot installation can be considered complete when all of the following checks have passed:

  • Windows boots normally without the Ventoy USB.
  • Debian boots normally without the Ventoy USB.
  • Windows reports BIOS Mode: UEFI.
  • Debian reports that it was booted in UEFI mode.
  • The internal system disk uses GPT.
  • The EFI System Partition is present and mounted correctly in Debian.
  • GRUB or the firmware boot menu provides a reliable path to both systems.
  • Windows and Debian both reach their normal desktop environments.
  • Networking, audio, graphics, storage, keyboard, mouse, and other required hardware work.
  • Fast Startup remains disabled in Windows.
  • The system clock remains correct after switching between operating systems.
  • Important files and backups remain accessible.
  • The Ventoy USB and recovery tools are kept available for future repairs.
Done: Both operating systems boot independently, the machine uses the intended UEFI/GPT configuration, the EFI and boot entries are understood, the basic hardware works, and recovery media is available if a future update or boot problem occurs.
XI / Linux 101

Linux 101

Debian is now installed and working, but using Linux effectively requires a basic understanding of how the system is organized. Unlike Windows, many administrative tasks are performed through the terminal, and system configuration is commonly represented by files and directories rather than separate graphical control panels.

This section introduces the practical fundamentals needed to operate and maintain a Debian desktop with KDE Plasma. It focuses on the commands, concepts, and troubleshooting habits that are useful in everyday use rather than attempting to document every part of Linux.

What you should understand

By the end of this section, you should be comfortable navigating the Linux filesystem, running commands with appropriate privileges, installing and updating software with APT, inspecting hardware and services, mounting storage, and performing basic troubleshooting.

You should also understand the difference between the Linux kernel, user space, the desktop environment, package management, and the boot process. These layers are separate, which makes it possible to troubleshoot one part of the system without unnecessarily changing another.

Linux is not one program. The kernel manages hardware, memory, processes, devices, and other core system functions. User-space programs provide the commands and services that you interact with, while KDE Plasma is the graphical desktop environment running on top of the underlying system.

A useful mental model

Think of a Linux system as several cooperating layers:

  • Firmware (UEFI): Initializes the hardware and starts the bootloader.
  • Bootloader (GRUB): Selects and starts an operating system and its kernel.
  • Kernel: Provides the core interface between software and hardware.
  • System services: Background processes such as networking, logging, device management, and scheduled tasks.
  • User space: Applications, command-line utilities, libraries, and configuration.
  • Desktop environment: KDE Plasma provides the graphical interface, panels, windows, settings, and desktop applications.

When something fails, identifying which layer is responsible is often more useful than immediately reinstalling software or changing configuration.

Root and normal users

Linux separates normal user privileges from administrative privileges. The root account has unrestricted control over the system. Debian normally expects administrative tasks to be performed through sudo rather than by working as root continuously.

For example: 

sudo apt update

Here, apt runs with administrative privileges only for that command. This reduces the chance that an ordinary command or mistake will modify the system unnecessarily.

Privilege warning: sudo does not make a command safer. It only gives the command more authority. Treat commands involving disks, partitions, filesystems, bootloaders, and recursive deletion as potentially destructive.

The Linux filesystem

Linux uses a single directory tree beginning at /, called the root filesystem. Storage devices are attached to this tree through mount points rather than being assigned drive letters such as C: or D:.

Some important locations include:

  • /home — personal files and user-specific configuration.
  • /etc — system-wide configuration files.
  • /var — changing system data such as logs and package data.
  • /usr — most installed programs, libraries, and shared data.
  • /boot — files required for booting, depending on the system layout.
  • /boot/efi — normally the mounted EFI System Partition on a UEFI installation.
  • /tmp — temporary files.
  • /dev — device nodes representing hardware and virtual devices.
  • /mnt and /media — common locations for mounted storage.

Linux also uses permissions to control who can read, write, or execute files. Understanding ownership and permissions becomes important when working with system files, scripts, shared directories, and mounted storage.

Terminal first, GUI when appropriate

KDE Plasma provides graphical tools for most everyday tasks, but the terminal exposes more detailed information and often provides the most direct way to diagnose a problem. Commands are also easier to reproduce and document than a sequence of graphical clicks.

This guide therefore uses both approaches. Use the graphical interface when it is clearer and safer, and use the terminal when it provides better visibility or control.

Good troubleshooting habit: Inspect before changing. First determine what the system currently sees, identify the component involved, and only then modify its configuration. This is especially important for disks, boot entries, networking, and system services.

The following pages build these skills progressively, starting with terminal basics and essential commands before moving into hardware, package management, maintenance, security, KDE Plasma, and finding reliable help.

XI.a / Terminal

Terminal Basics

The terminal is a text-based interface for interacting directly with Linux. It is not a separate operating system or a replacement for KDE Plasma; it is simply another way to communicate with the system and run programs.

Opening a terminal

In KDE Plasma, open Konsole from the application menu. A terminal normally displays a prompt similar to: 

user@debian:~$

The prompt shows useful context. The text before @ is the current username, the text after it is the hostname, and ~ represents the current user's home directory. A prompt ending in $ normally indicates a regular user. A # generally indicates a root shell.

Running a command

Type a command and press Enter. For example: 

pwd

The command prints the current working directory. Most Linux commands follow the general form: 

command [options] [arguments]

For example: 

ls -lah /var/log

Here, ls is the command, -lah supplies options, and /var/log is the argument specifying what should be listed.

Getting help

Most commands provide built-in help: 

command --help

Linux also provides manual pages: 

man command

For example: 

man ls

Press q to leave a manual page. You do not need to memorize every command or option; knowing how to find authoritative information is more useful.

Paths and the home directory

Linux paths use / as the directory separator. An absolute path starts with /, while a relative path is interpreted from the current directory. 

pwd
                cd /etc
                cd ..
                cd ~

.. means the parent directory and ~ represents your home directory. Linux filenames are case-sensitive, so Documents and documents are different names.

Useful shell shortcuts

  • Tab — completes commands, paths, and filenames.
  • ↑ / ↓ — move through command history.
  • Ctrl + C — interrupt the currently running command.
  • Ctrl + L — clear the visible terminal screen.
  • Ctrl + Shift + V — paste into Konsole.
Be careful with pasted commands: A command copied from the internet can modify files, install software, or execute code. Read the command and understand what it does before running it, especially when it uses sudo, pipes, redirection, or recursive deletion.

Command output and errors

A command may produce output on the terminal or return silently when it succeeds. Errors are commonly printed separately and may include a useful explanation. Do not ignore an error simply because the command returned to the prompt.

Linux commands also return an exit status. A status of 0 normally means success, while a non-zero value indicates some kind of failure: 

echo $?

This is particularly useful when troubleshooting scripts and commands whose output is not immediately obvious.

XI.b / Commands

Essential Linux Commands

The following commands cover most basic navigation, file management, inspection, and troubleshooting tasks. Learn what each command is for rather than trying to memorize every option.

Navigation and files

pwd
                ls
                ls -lah
                cd directory
                mkdir directory
                touch file.txt
                cp source destination
                mv source destination
                rm file.txt
  • pwd shows the current directory.
  • ls lists files and directories.
  • cd changes the current directory.
  • mkdir creates a directory.
  • touch creates an empty file when the file does not exist.
  • cp copies files or directories.
  • mv moves or renames files.
  • rm removes files.
Deletion is immediate: rm normally does not move files to the KDE Trash. Be especially careful with rm -r and never add recursive or force options without understanding exactly what path they affect.

Inspecting files

cat file.txt
                less file.txt
                head file.txt
                tail file.txt
                grep "text" file.txt
                find /path -name "filename"

cat prints a file, while less is better for large files because it allows you to scroll through the contents. head and tail show the beginning and end of a file. grep searches text, and find searches for files matching specified conditions.

System logs are often easier to inspect with: 

journalctl

For example, recent errors can be filtered with: 

journalctl -p err -b

This displays error-priority messages from the current boot. The system journal is one of the most useful sources of information when diagnosing services, drivers, boot problems, and hardware events.

Processes and system resources

ps aux
                top
                free -h
                df -h
                du -sh directory

ps lists running processes, top provides a live process view, and free -h shows memory usage. df -h reports filesystem space, while du -sh estimates how much space a directory consumes.

Hardware and storage

lsblk
                lsblk -f
                lspci
                lsusb
                lscpu
                free -h

lsblk displays block devices and their partition relationships. lsblk -f additionally shows filesystem information. lspci lists PCI devices such as GPUs and network controllers, while lsusb lists USB devices. lscpu reports processor information.

Permissions and ownership

ls -l
                chmod
                chown

Linux permissions determine whether the file owner, members of its group, and other users can read, write, or execute a file. chmod changes permissions and chown changes ownership.

Do not routinely use sudo to solve permission problems without understanding why the permissions are incorrect. Changing ownership or permissions recursively can break applications or system services.

Running administrative commands

Use sudo when a command requires administrative privileges: 

sudo command

Your password may be requested. Nothing is displayed while a password is being typed; this is normal.

Practical rule: Use normal user privileges whenever possible. Use sudo only for the specific operation that requires it, and inspect the command before confirming it.

Command composition

Linux commands can be combined using shell operators. A pipe sends the output of one command into another: 

ls -lah /var/log | less

The && operator runs the next command only if the previous command succeeds: 

sudo apt update && echo "Update completed"

These features make the terminal powerful, but they also mean that a single pasted line can perform several operations. Read compound commands carefully before executing them.

Core skill: You do not need to know hundreds of commands. If you can navigate the filesystem, inspect files and hardware, understand permissions, manage processes, read logs, and find command documentation, you can handle most routine Linux administration tasks.
XI.c / Shell

Terminal Survival Guide

The Linux terminal becomes much more useful once you understand the shell itself. On Debian, the default interactive shell is normally Bash (Bourne Again SHell). Bash reads commands, expands variables and paths, connects programs together, and controls how commands are executed.

A terminal emulator such as Konsole provides the window, while Bash is the shell running inside it. They are separate components. You can therefore change shells without replacing the terminal application.

Bash basics

Check which shell is currently running: 

echo $SHELL
                    echo $0

Bash commands generally follow this structure: 

command [options] [arguments]

For example: 

ls -lah /var/log

Bash also performs processing before the program receives the arguments. This includes variable expansion, wildcard expansion, command substitution, quoting, and redirection.

Variables

Variables store values that can be used by commands and scripts. Environment variables provide information about the current session and system: 

echo $HOME
                    echo $USER
                    echo $PATH

$HOME is the user's home directory, $USER normally contains the current username, and $PATH tells Bash where to search for executable commands.

You can create a temporary shell variable with: 

name="Debian"
                    echo "$name"

Spaces around = are not allowed in a normal Bash variable assignment. Quoting variables is generally a good habit because it prevents spaces and special characters from being interpreted unexpectedly.

Quoting

Quotes control how Bash interprets text: 

echo "Hello $USER"
                    echo 'Hello $USER'

Double quotes allow variable expansion, while single quotes preserve the text literally. This distinction becomes important when working with filenames, scripts, and commands containing spaces or special characters.

Wildcards

Bash can expand wildcards before a command runs: 

ls *.txt
                    ls image-?.png

* matches zero or more characters and ? matches one character. This is called pathname expansion or globbing.

Be careful with wildcards: A command such as rm *.tmp can affect many files at once. Always check what a wildcard expands to before using it with destructive commands.

Pipes

A pipe connects the standard output of one command to the standard input of another. The pipe operator is |. 

ls -lah /var/log | less

Here, ls produces a directory listing and less receives that output so it can be viewed page by page.

Pipes are one of the most important concepts in Unix-like systems because small programs can be combined to perform more useful operations: 

journalctl -b | grep -i error

This sends the current boot's journal into grep, which filters the output for lines containing "error", ignoring case.

Redirection

Commands normally read from standard input and write to standard output. Bash allows these streams to be redirected. 

command > output.txt
                    command >> output.txt
                    command < input.txt

> creates or replaces a file, while >> appends to it. The < operator supplies a file as standard input.

Standard error can also be redirected. A common example is: 

command >output.txt 2>error.txt

This keeps normal output and error messages in separate files. To combine standard output and standard error: 

command >output.txt 2>&1

Command chaining

Bash provides several operators for controlling whether commands continue: 

command1 && command2
                    command1 || command2
                    command1 ; command2

&& runs the second command only when the first succeeds. || runs it when the first command fails. A semicolon runs the commands sequentially regardless of the previous command's exit status.

For example: 

sudo apt update && sudo apt full-upgrade

The upgrade will not start if updating the package indexes fails.

Command substitution

Bash can use the output of one command as part of another command: 

echo "Kernel: $(uname -r)"

The expression inside $(...) is executed first and its output is inserted into the surrounding command. This is extremely useful in shell scripts.

What is .bashrc?

~/.bashrc is a configuration file read by Bash when it starts an interactive non-login shell. It is commonly used for aliases, shell functions, environment settings, and prompt customization.

View it with: 

less ~/.bashrc

To edit it: 

nano ~/.bashrc

After making changes, start a new terminal or reload the file: 

source ~/.bashrc
Do not confuse Bash configuration files: ~/.bashrc is primarily for interactive non-login Bash shells. Login shells may instead read files such as ~/.bash_profile or ~/.profile. On Debian, ~/.profile commonly ensures that ~/.bashrc is loaded for an appropriate interactive Bash session.

Aliases

An alias gives a short name to a frequently used command: 

alias ll='ls -lah'

Adding the alias to ~/.bashrc makes it available in future interactive Bash sessions: 

echo "alias ll='ls -lah'" >> ~/.bashrc
                    source ~/.bashrc

Avoid aliases that hide potentially destructive commands or make a command behave differently from its documented form. A useful alias should save typing without making the command's behavior surprising.

Functions and your first command

When an alias is not flexible enough, Bash functions can accept arguments and perform several operations: 

mkcd() {
                        mkdir -p "$1" && cd "$1"
                    }

After placing the function in ~/.bashrc and running source ~/.bashrc, you can use: 

mkcd ~/test-directory

$1 represents the first argument supplied to the function. Always quote variables such as "$1" when they represent paths, because filenames can contain spaces.

Writing a simple Bash script

A series of Bash commands can be saved as a script instead of typed repeatedly: 

#!/usr/bin/env bash

                echo "System information"
                uname -r
                df -h /

Save the file, make it executable, and run it: 

chmod +x system-info.sh
                    ./system-info.sh

The first line, called a shebang, tells the system which interpreter should execute the script. Using #!/usr/bin/env bash asks env to locate Bash using the current environment.

Exit status and debugging

Every command normally finishes with an exit status. Bash stores the status of the most recently executed command in $?: 

some-command
                    echo $?

A value of 0 conventionally means success; non-zero values indicate an error or another condition defined by the program.

When writing more serious scripts, Bash's strict-mode options can help expose mistakes: 

set -euo pipefail

These options can make scripts fail earlier, but they also have edge cases and should not be added blindly to scripts copied from elsewhere. For simple personal commands, understanding exit status and checking command output is usually enough.

Finding the command Bash will run

If you are unsure where a command comes from, use: 

type ls
                    command -v ls
                    type -a python3

These commands help determine whether a name is a shell builtin, alias, function, or executable found through PATH. This is useful when a command behaves differently from what you expect.

Terminal survival rule: Read the command before pressing Enter. Understand its target path, required privileges, wildcard expansion, pipes, redirections, and destructive operations. Bash is powerful precisely because it allows simple commands to be combined into very powerful ones.
IX.d / System

Hardware, Drivers, and Firmware

Linux handles hardware through the kernel, kernel modules, firmware files, and userspace drivers and services. Most common hardware works automatically, but knowing how to inspect the system makes troubleshooting much easier.

The first rule is to identify the hardware before changing drivers. Do not install a random driver package simply because a device is not behaving as expected.

Identify the hardware

lshw provides a detailed inventory of the system: 

sudo lshw -short
                sudo lshw -C display
                sudo lshw -C network

lspci is particularly useful for PCIe devices such as graphics cards, Wi-Fi adapters, Ethernet controllers, and storage controllers: 

lspci
                lspci -nnk

The -k option shows the kernel driver currently associated with each device. The -nn option also displays the PCI vendor and device IDs, which are useful when searching documentation for an exact piece of hardware.

USB devices can be inspected with: 

lsusb
                lsusb -t

Storage devices can be identified with: 

lsblk -o NAME,SIZE,TYPE,FSTYPE,LABEL,MODEL,SERIAL,TRAN
Useful distinction: A kernel driver is the software that allows the Linux kernel to communicate with a hardware device. Firmware is code that is loaded into the hardware itself or supplied to it by the operating system. They are related, but they are not interchangeable.

Check loaded drivers and kernel messages

To see loaded kernel modules: 

lsmod

To determine which driver a particular PCI device is using: 

lspci -k

Kernel messages are often the fastest way to find hardware initialization problems: 

sudo dmesg --level=err,warn
                sudo dmesg | less

On systems using systemd, the kernel log can also be viewed with: 

journalctl -k
                journalctl -k -b

-b limits the output to the current boot. This is particularly useful when a device works intermittently or fails during startup.

Graphics drivers

Graphics hardware is one of the more driver-sensitive parts of a Linux desktop. First identify the GPU and the driver currently in use: 

lspci -nnk | grep -A3 -E 'VGA|3D|Display'

On Debian, prefer the official Debian packages and documentation for the detected GPU rather than downloading an installer directly from a random website.

NVIDIA systems can require additional proprietary firmware and driver packages. AMD and Intel graphics generally use drivers integrated into the Linux kernel and Mesa userspace stack. The exact requirements depend on the hardware generation and Debian release.

Do not mix graphics-driver sources casually. Combining Debian packages, third-party repositories, and vendor-provided installer scripts can create conflicting libraries or kernel modules. Prefer one supported driver source and change it deliberately.

Wi-Fi and Bluetooth

Identify network interfaces with: 

ip link
                lspci -nnk | grep -A3 -i network
                lsusb | grep -i -E 'wifi|wireless|bluetooth'

NetworkManager can show the devices and their current state: 

nmcli device status
                nmcli device show

If Wi-Fi or Bluetooth is missing, check the kernel log for firmware or driver errors: 

sudo dmesg | grep -iE 'firmware|wifi|wlan|bluetooth|iwlwifi|ath|rtw'

Many wireless devices require firmware packages. On Debian 13, make sure non-free-firmware is enabled as described in the repository section of this guide.

Install or update drivers

Debian normally distributes kernel modules and userspace drivers through APT. Start by updating the package information: 

sudo apt update

Search for packages related to the hardware only after identifying the device: 

apt search firmware
                apt search nvidia
                apt search mesa

Debian also provides the firmware-linux packages and many device-specific firmware packages. The appropriate package depends on the hardware, so installing every firmware package is usually unnecessary.

After installing a new kernel or driver, reboot when appropriate so that the new kernel modules and firmware are loaded from a clean boot.

Firmware and BIOS/UEFI updates

System firmware is different from Linux drivers. BIOS/UEFI firmware is provided by the computer or motherboard manufacturer and runs before the operating system. Device firmware may instead be distributed through Linux packages.

On supported hardware, Debian can use fwupd and the Linux Vendor Firmware Service (LVFS) to discover and install firmware updates: 

sudo apt install fwupd
                sudo systemctl enable --now fwupd
                fwupdmgr get-devices
                fwupdmgr get-updates

If an update is available, review it before installing: 

fwupdmgr update

Some updates require a reboot and are applied by the system firmware during the next startup.

Firmware updates require extra care: Keep the computer connected to reliable power, do not interrupt the update, and follow any manufacturer-specific instructions. A failed system-firmware update can prevent the machine from booting.

Check firmware support

You can inspect whether fwupd considers the system supported: 

fwupdmgr get-devices
                fwupdmgr get-remotes

Not every motherboard or device supports firmware updates through fwupd. If nothing is offered, check the hardware manufacturer's support documentation rather than assuming that firmware is outdated.

Useful hardware checks

These commands are useful during everyday troubleshooting: 

lscpu
                free -h
                lsblk
                lspci -nnk
                lsusb
                ip -br link
                sudo sensors

lscpu reports processor information, free -h reports memory usage, lsblk describes storage devices, lspci and lsusb inspect hardware buses, and sensors reports temperatures and other hardware sensors when supported.

If sensors is not installed: 

sudo apt install lm-sensors
                sudo sensors-detect
                sensors

Do not blindly accept every recommendation from sensors-detect. Most modern systems work with automatically detected sensor modules.

When hardware is not working

Follow a simple diagnostic order:

  1. Identify the physical device with lspci, lsusb, or lsblk.
  2. Check which kernel driver is being used with lspci -k or the relevant subsystem tools.
  3. Check dmesg or journalctl -k for driver and firmware errors.
  4. Confirm that the required Debian firmware or driver package is installed.
  5. Check whether the device is blocked, disabled in firmware, or simply disconnected.
  6. Search the exact hardware model and error message in Debian's documentation and bug database.
Useful rule: "No driver installed" is only one possible cause. Hardware can also fail because of missing firmware, an unsupported device revision, a disabled BIOS/UEFI setting, a kernel regression, power-management behavior, or a physical fault.

IX.e / Packages

Package Management

Debian manages software primarily through APT. APT (Advanced Package Tool) resolves dependencies, downloads packages from configured repositories, installs them, and keeps the system's installed software consistent.

Debian packages normally use the .deb format. A package contains the program itself, metadata, configuration information, and dependency information. APT uses this information to determine what must be installed alongside it.

APT vs. dpkg: dpkg is the lower-level tool that directly installs and manages individual .deb packages. APT operates at a higher level and handles repositories, dependency resolution, downloads, and upgrades. For normal package management, prefer APT.

Update the package index

Before installing or upgrading software, refresh the local package indexes: 

sudo apt update

This does not upgrade installed software. It downloads current repository metadata so APT knows which package versions are available.

Run apt update whenever you are about to install software and the package information may be outdated, or after changing the repository configuration.

Install packages

Install one or more packages with: 

sudo apt install package-name
                sudo apt install package-one package-two package-three

APT calculates the dependencies required by the requested packages and normally installs them automatically. It will show the packages that will be installed, upgraded, or removed before asking for confirmation.

If you know the exact package name, APT can also install a specific version: 

apt policy package-name
                sudo apt install package-name=version

apt policy is useful for seeing the installed version, candidate version, and repositories from which versions are available.

Search for software

Search the configured repositories with: 

apt search keyword

For more focused information about a package: 

apt show package-name

This can display its description, version, dependencies, download size, installed size, and other package metadata.

Upgrade the system

The normal workflow for keeping Debian updated is: 

sudo apt update
                        sudo apt upgrade

apt upgrade upgrades installed packages when doing so does not require removing packages or making more significant dependency changes.

For a complete upgrade where dependency changes may be required, use: 

sudo apt full-upgrade

full-upgrade may install additional packages or remove packages when necessary to complete the upgrade. Read the proposed changes before confirming, especially if APT proposes removing important desktop or system packages.

Do not blindly accept removals. If an ordinary update suddenly proposes removing a large part of KDE Plasma, networking, the kernel, or another important part of the system, stop and investigate the dependency change before proceeding.

Remove and purge packages

A package can be removed with: 

sudo apt remove package-name

remove normally removes the installed program while leaving its system-wide configuration files behind. To remove the package and its configuration files: 

sudo apt purge package-name

Be careful with purge. Configuration files may contain settings you would want to keep if you later reinstall the package.

Handle unused dependencies

APT tracks packages that were installed automatically as dependencies of other packages. When those dependencies are no longer required, they may become removable: 

sudo apt autoremove

Review the proposed removal list before confirming. Do not treat autoremove as a command that should always be run without inspection.

Understand repositories

APT obtains packages from configured Debian repositories. The repository configuration determines which Debian release, components, and package sources APT is allowed to use.

On Debian 13, repository configuration is commonly stored in /etc/apt/sources.list.d/debian.sources using the deb822 format. Inspect it with: 

cat /etc/apt/sources.list.d/debian.sources

You can also inspect all configured sources with: 

grep -R -E '^(Types:|URIs:|Suites:|Components:)' \
                /etc/apt/sources.list /etc/apt/sources.list.d/ 2>/dev/null

A normal Debian Stable installation should use repositories appropriate for the installed Debian release. Do not add repositories for Testing, Unstable, Ubuntu, or unrelated third-party distributions simply to obtain one newer package.

Backports

Debian Backports provides selected newer packages rebuilt for the current Stable release. If Backports has been enabled as described earlier in this guide, a package can be requested explicitly: 

sudo apt install package-name/trixie-backports

This allows newer software to be used without turning the entire system into a mixture of Debian Stable and Testing or Unstable packages.

Inspect packages and dependencies

APT provides several useful ways to understand what it is about to do: 

apt policy package-name
                apt show package-name
                apt depends package-name
                apt-cache depends package-name

These commands are particularly useful when diagnosing dependency problems or deciding which package provides a particular feature.

To see which installed package owns a file: 

dpkg -S /path/to/file

To list files installed by a package: 

dpkg -L package-name

Installing a downloaded .deb

A local Debian package can be installed with APT: 

sudo apt install ./package-name.deb

The ./ tells APT that the argument refers to a local file rather than a package name from the repositories. Using APT for a local .deb is preferable to manually using dpkg -i when possible because APT can resolve dependencies from the configured repositories.

Third-party .deb files: A package can have legitimate Debian packaging while still coming from an untrusted source. Only install downloaded packages when you trust the publisher and understand what repository or software is being added.

When APT reports broken dependencies

If an interrupted installation leaves packages in an incomplete state, first allow APT to repair pending dependencies: 

sudo apt --fix-broken install

Then refresh the package indexes and complete the upgrade if necessary: 

sudo apt update
                sudo apt full-upgrade

Do not start deleting packages at random to resolve dependency errors. APT's proposed changes and the package relationships should be understood first.

Useful APT commands

sudo apt update
                sudo apt install package-name
                sudo apt remove package-name
                sudo apt purge package-name
                sudo apt upgrade
                sudo apt full-upgrade
                sudo apt autoremove
                apt search keyword
                apt show package-name
                apt policy package-name
                apt list --installed
                apt list --upgradable
Good package-management habit: Keep Debian's repositories consistent with the installed Debian release, update the package index before major package operations, review APT's proposed changes, and prefer APT over manually installing individual packages whenever a package is available from Debian's repositories.

References

Debian's official documentation provides further information about package management and the APT system:

Debian Handbook — The APT Package Management System · Debian APT Wiki · Debian apt(8) manual

IX.f / Maintenance

Updating and Maintenance

A Debian system does not normally require constant maintenance. The important tasks are keeping packages updated, checking the health of the filesystem and storage, removing unnecessary packages when appropriate, and periodically reviewing logs and system resources.

Keep Debian updated

The normal update cycle is: 

sudo apt update
                sudo apt upgrade

Use full-upgrade when dependency changes are required: 

sudo apt full-upgrade

Read the proposed changes before confirming. Pay particular attention to packages being removed, especially kernels, desktop packages, networking components, or boot-related packages.

Kernel updates are normal. Debian may keep more than one installed kernel so that an older kernel can be selected from GRUB if a newly installed kernel has a problem. Do not manually remove the currently running kernel.

Restart when appropriate

Most normal package updates do not require a reboot. Kernel updates and certain low-level libraries or services may, however, make a reboot desirable.

Check whether Debian recommends a reboot: 

test -f /var/run/reboot-required && echo "Reboot recommended"

When required: 

sudo reboot

Remove unused packages

Packages installed automatically as dependencies can become unnecessary after other software is removed: 

sudo apt autoremove

Review the list before confirming. If an apparently important package is going to be removed, stop and investigate why it is considered unnecessary.

Check available disk space

A full filesystem can cause anything from failed updates to application crashes. Check mounted filesystems with: 

df -h

To find which directories are consuming space: 

sudo du -xhd1 / | sort -h

For a user's home directory: 

du -hd1 ~ | sort -h

Large log files, package caches, virtual machines, containers, downloads, and old kernels are common sources of unexpected disk usage.

Clean the APT cache

APT keeps downloaded package files in its local cache. They can normally be removed safely when disk space is needed: 

sudo apt clean

apt autoclean is more conservative and removes cached package files that can no longer be downloaded: 

sudo apt autoclean
Do not make cache cleaning a routine obsession. The cache is normally small compared with modern disk capacities, and keeping some packages cached can make reinstalls faster.

Inspect system logs

Debian uses systemd and its journal on a standard installation. View recent system messages with: 

journalctl -b
                journalctl -p warning..alert -b
                journalctl -k -b

The first command shows messages from the current boot. The second focuses on warnings and more serious messages, while the third shows kernel messages.

To inspect the previous boot, which is useful when diagnosing a failed startup: 

journalctl -b -1

Check running services

List failed systemd units: 

systemctl --failed

Inspect a particular service with: 

systemctl status service-name

Avoid disabling services simply because they appear unfamiliar. Some services are dependencies of desktop, networking, storage, or hardware functionality.

Check storage health

For supported SATA, SAS, and NVMe drives, SMART information can provide useful indicators of drive health. Install the required tools: 

sudo apt install smartmontools

For a SATA/SAS drive, for example: 

sudo smartctl -a /dev/sdX

For an NVMe drive: 

sudo smartctl -a /dev/nvme0n1

Replace the device name with the actual drive identified using lsblk. Do not assume that /dev/sda is the target drive.

SMART is not a guarantee. A drive can fail without showing an obvious SMART warning, and some controllers expose only limited health information. Important data should therefore remain backed up regardless of reported drive health.

Check memory and system load

Basic resource information can be checked with: 

free -h
                uptime
                top

If htop is installed, it provides a more convenient interactive process and resource view: 

htop

High CPU or memory usage is not automatically a fault. Identify the process responsible before terminating anything.

Review failed boots and shutdowns

When troubleshooting startup problems, list previous boots: 

journalctl --list-boots

Then inspect a specific boot using its index: 

journalctl -b -1

This is often more useful than guessing which service caused a problem.

Keep backups separate from maintenance

System maintenance is not a substitute for backups. Package updates, filesystem errors, accidental deletion, hardware failure, and user mistakes can all cause data loss.

Important files should continue to have an independent backup, preferably with at least one copy that is not permanently connected to the computer.

Do not over-maintain Debian

Avoid routine use of aggressive cleanup scripts, manually deleting files under /usr or /var, removing packages merely because they look unused, or installing unofficial "system optimizer" tools. Debian's package manager and normal system utilities are generally sufficient.

Good maintenance routine: Update APT regularly, install available security and normal updates, reboot when appropriate, monitor disk space, investigate failed services or serious log messages, keep storage and backups healthy, and avoid changing a working system without a reason.
IX.g / Security

Security Basics

A secure Debian desktop does not require dozens of security tools. The important basics are keeping the system updated, limiting exposed services, using least privilege, protecting accounts, and understanding what is actually reachable from the network.

Keep the system updated

Security updates are normally delivered through Debian's regular repositories. Keep the package index current and install available updates: 

sudo apt update
                sudo apt upgrade

Avoid delaying security updates for long periods, particularly for systems that are connected to untrusted networks.

Use sudo instead of logging in as root

The root account has unrestricted control over the system. Debian's normal desktop workflow is to use a regular account and elevate individual administrative commands with sudo. 

sudo command

This limits the amount of time a command is running with administrative privileges and makes accidental system-wide changes less likely.

Privilege matters: A command executed through sudo can modify or delete almost anything on the system. Treat commands copied from the internet with the same care as programs you would install.

AppArmor

AppArmor is a Linux security framework that restricts what selected applications are allowed to access. Instead of relying only on Unix file permissions, AppArmor can confine a process to a defined security profile.

Check whether AppArmor is running: 

sudo aa-status

On Debian, install it if it is not already present: 

sudo apt install apparmor apparmor-utils
                sudo systemctl enable --now apparmor

Existing profiles can be inspected with: 

sudo aa-status
                ls /etc/apparmor.d/

Do not put arbitrary applications into enforcing mode without understanding their profiles. A restrictive profile can legitimately prevent an application from accessing files or capabilities that it needs.

AppArmor is not antivirus. It is an access-control mechanism that limits what a confined process can do if it is compromised or behaves unexpectedly.

Firewall basics

A firewall controls network traffic entering or leaving the computer according to defined rules. A desktop that does not provide network services usually has fewer inbound connections to protect than a server, but a firewall is still useful on untrusted networks.

Debian provides several firewall technologies. nftables is the modern packet-filtering framework in the Linux kernel. For a simple desktop configuration, UFW provides an easier command-line interface for managing firewall rules.

Install UFW: 

sudo apt install ufw

A basic desktop policy can deny unsolicited incoming connections while allowing outgoing connections: 

sudo ufw default deny incoming
                sudo ufw default allow outgoing
                sudo ufw enable

Check the resulting configuration: 

sudo ufw status verbose
Be careful over SSH: If you are connected to the machine remotely through SSH, enabling a firewall without first allowing SSH can disconnect you. On a normal local desktop this is usually not an issue, but it matters for remotely administered systems.

Ports and listening services

A network port identifies a service endpoint associated with a transport protocol such as TCP or UDP. A service that is listening on a port can potentially accept network traffic, subject to firewall rules and the service's own authentication and access controls.

See which services are currently listening: 

sudo ss -tulpn

The most important columns include the protocol, local address, port, and process. For example, a service listening on 0.0.0.0:22 is listening on TCP port 22 on all IPv4 interfaces, while 127.0.0.1:PORT is normally reachable only from the local machine.

If a service is not needed, stop and disable it rather than simply relying on the firewall: 

sudo systemctl status service-name
                sudo systemctl disable --now service-name

Only disable a service after confirming what depends on it.

Allowing a required port

If you intentionally run a service, allow only the required port. For example, SSH normally uses TCP port 22: 

sudo ufw allow 22/tcp

Then verify the rules: 

sudo ufw status numbered

Prefer restricting administrative services to trusted networks when possible. Opening a port to the entire internet simply because an application needs it increases its exposure.

A port is not the vulnerability. An open port is an indication that something is listening. Security depends on what service is behind it, how it is configured, whether it is patched, and who can reach it.

Containers and isolation

Containers package applications and their dependencies while using the host kernel. They provide useful process, filesystem, and network isolation, but they are not equivalent to a virtual machine and should not be treated as a perfect security boundary.

If you use containers, prefer rootless operation where practical and obtain images from sources you trust. Keep the container runtime and images updated.

For Docker-based systems, remember that publishing a container port can make it reachable from the host or network: 

docker ps
                docker port container-name

Do not publish administrative interfaces or databases to all network interfaces unless that exposure is intentional.

Container networking can bypass assumptions: Some container runtimes create their own firewall and NAT rules. Always verify actual listening sockets and network exposure rather than assuming that a host firewall rule alone tells the complete story.

File permissions

Linux uses ownership and permission bits to control access to files and directories. Inspect them with: 

ls -l /path/to/file
                stat /path/to/file

Avoid making files or directories world-writable with commands such as chmod 777 unless there is a very specific and understood reason. Giving every local user write access is rarely the correct solution to a permissions problem.

For sensitive files, check both ownership and permissions: 

namei -l /path/to/file

SSH basics

If SSH is required, install the server only when needed: 

sudo apt install openssh-server
                sudo systemctl enable --now ssh

Check that it is listening: 

sudo ss -tlnp | grep ':22'

Prefer SSH keys over password authentication for administrative access. Keep the SSH server updated and restrict access with the firewall when possible.

Do not change SSH configuration simply by copying a hardening checklist. Test the configuration before restarting the service: 

sudo sshd -t

Basic account and network habits

  • Use a normal user account for everyday work.
  • Use sudo only for commands that require administrative privileges.
  • Install software from Debian repositories or trusted publishers.
  • Keep the kernel, applications, firmware, and container images updated.
  • Do not expose services to the network unless they are actually required.
  • Use a firewall on networks where unsolicited inbound traffic is possible.
  • Be especially careful on public Wi-Fi and other untrusted networks.
  • Keep important data backed up independently of the system.
Good baseline: Keep Debian updated, use a normal account with sudo, keep AppArmor enabled, deny unnecessary inbound traffic, know which ports are listening, expose only required services, and treat containers and third-party software as additional components that need their own security controls.

References

Useful Debian and upstream documentation:

Debian AppArmor documentation · Debian UFW documentation · nftables Wiki · Docker Engine security documentation · Debian ss(8) manual

VIII.h / Desktop

KDE Plasma Guide

KDE Plasma is Debian's desktop environment in this guide. It provides the graphical desktop, application launcher, taskbar, system tray, settings tools, window management and desktop customization.

The desktop

The bottom panel normally contains the application launcher, pinned applications, running windows, system tray, network controls, volume, notifications and the clock. The desktop itself can also contain files, folders and widgets.

The application launcher can be opened from the panel or with the Meta key. Use it to search for installed applications, settings and files rather than manually browsing application menus.

System Settings

System Settings is the main configuration interface for Plasma. The most commonly used areas include:

  • Display & Monitor: resolution, scaling, refresh rate and multiple displays.
  • Input Devices: keyboard, mouse, touchpad and other input settings.
  • Network: Wi-Fi, Ethernet, VPN and connection configuration.
  • Audio: output devices, microphones and volume profiles.
  • Appearance: themes, colors, icons, fonts and visual style.
  • Window Management: window behavior, shortcuts and effects.
  • Power Management: screen timeout, sleep and battery behavior.

Windows and workspaces

Plasma supports virtual desktops and multiple windows. Applications can be switched with Alt + Tab, while virtual desktops can be managed through the desktop overview or configured in System Settings.

Window actions such as maximizing, minimizing, moving and tiling can be performed with the mouse or configured keyboard shortcuts. Plasma's window manager, KWin, handles these operations as well as many display and compositing features.

Installing applications

Debian packages should normally be installed through APT rather than by downloading random installer files from the internet. KDE's graphical software-management tools can also be used when available, but the terminal remains useful for administration: 

apt search package-name
                sudo apt install package-name

Applications installed through APT are integrated with Debian's package database and receive updates through the normal system update process.

Basic customization

Plasma is highly configurable, but extensive customization is optional. Panel position, widgets, themes, wallpapers, icons and shortcuts can all be changed without modifying the underlying Debian system.

Keep the desktop predictable: Avoid installing large collections of third-party themes, widgets or unofficial system tweaks until the base installation is known to work. When troubleshooting later, a mostly stock Plasma configuration makes it easier to distinguish desktop problems from hardware or system problems.

Useful keyboard shortcuts

  • Meta — open the application launcher.
  • Alt + Tab — switch between applications.
  • Alt + F2 — open Plasma's command/search interface.
  • Ctrl + Alt + T — commonly opens a terminal, depending on the configured shortcuts.
  • Meta + L — lock the screen.

Shortcuts can be changed under System Settings → Keyboard → Shortcuts. The exact available shortcuts can vary with the Plasma version and configuration.

Practical goal: Learn where applications, system settings, networking, displays, audio and power controls are located. Most day-to-day Plasma configuration can be performed graphically, while APT and the terminal remain available for deeper system administration.
VIII.i / Documentation

Finding Help

Linux systems provide extensive documentation locally and online. The most useful skill is not memorizing every command, but knowing how to discover what a command does, find the relevant option, and verify the information before using it.

Use man first

man (manual) pages are the traditional reference documentation for Linux commands, configuration files, system calls and other interfaces. 

man ls
                man apt
                man systemctl
                man 5 fstab

The number after a command selects a particular manual section. For example, section 1 normally contains user commands, while section 5 commonly contains file formats and configuration files. man -k can search manual-page descriptions: 

man -k filesystem
                man -k network

Inside a manual page, use /word to search, n to move to the next match, and q to quit. This is often much faster than reading an entire manual from beginning to end.

Command-specific help

Many commands provide a short built-in help screen: 

command --help
                command -h

This is usually the quickest way to check syntax and commonly used options. For more complete information, use the corresponding manual page.

Shell built-ins are slightly different. Bash commands such as cd, export, alias and source may not have independent executables. Bash provides their documentation through help: 

help cd
                help export
                help source

You can also determine whether a command is a shell built-in, alias, function or external executable: 

type cd
                type ls
                type command-name

Use tldr for practical examples

tldr provides short, example-oriented summaries of many common commands. It is useful when you know roughly what you want to do but do not want to read a complete manual page first. 

tldr rsync
                tldr tar
                tldr find

Treat tldr as a quick reference rather than a replacement for the official documentation. When an operation is destructive, security sensitive, or unfamiliar, read the actual manual or project documentation before running it.

Search locally

When you do not know the exact command, search by describing the task: 

apropos "disk partition"
                apropos network
                man -k archive

You can also inspect where an executable comes from: 

command -v git
                which git
                type git

For installed Debian packages, dpkg can show which package owns a file and which files belong to a package: 

dpkg -S /usr/bin/curl
                dpkg -L curl

Reading large documentation and wikis

Large documentation sites and wikis are easier to use when treated as reference material rather than something that must be read from start to finish.

  1. Start with the overview or installation page to understand the project's terminology and structure.
  2. Use the page's table of contents and browser search (Ctrl + F) to locate the relevant section.
  3. Follow links when a term or prerequisite is unfamiliar instead of guessing its meaning.
  4. Check the documentation version. Instructions for Debian Stable, Testing, another distribution, or an older software release may differ.
  5. Read warnings, prerequisites and examples surrounding the command you intend to use, not just the command itself.

For command-line documentation, a useful pattern is to first identify the command with type or command -v, check --help, then read man or the project's official documentation when more detail is required.

Search engines and community answers

Search engines are useful for finding documentation, bug reports and troubleshooting discussions. Prefer the project's official documentation, Debian documentation and upstream issue trackers when available.

Community sites can provide valuable real-world solutions, but verify commands against current documentation before executing them. A command that was correct for an older release can be inappropriate or dangerous on a current system.

Do not blindly copy commands: Pay particular attention to commands containing sudo, rm, dd, partitioning tools, filesystem tools, redirections such as >, or commands downloaded and executed directly from the internet. Understand what the command changes before running it.

Useful documentation sources

  • Debian Manpages — searchable Debian manual pages.
  • Debian Documentation — Debian manuals, guides and reference material.
  • GNU Bash Reference Manual — detailed Bash documentation.
  • tldr — concise command examples and quick references.
Good troubleshooting habit: Identify the command or component, check its built-in help and manual, reproduce the problem carefully, and then search for the exact error message. Understanding why a command works is much more useful than collecting commands that happen to fix one particular problem.
IX / Dual-Boot Usage

Using Windows and Debian Together

With both systems installed, the dual-boot setup is simply a matter of choosing which operating system to use at startup. Each system remains independently installed, while shared storage can be used to move data between them.

Keep the systems independent: Avoid modifying Windows system partitions from Linux or Linux system partitions from Windows unless there is a specific reason and the filesystem is known to be safe to access.
IX.a / Files

Sharing files between systems

The simplest way to share ordinary files is to use a dedicated data partition formatted with a filesystem that both systems can access. NTFS is a practical choice when the partition needs to be writable from both Windows and Debian.

Keep shared documents, media and other common files on this partition rather than placing them inside either operating system's system directories.

Windows shutdown matters: Do not write to an NTFS Windows partition from Debian while Windows is hibernated or Fast Startup is enabled. Fully shut down Windows before accessing its writable NTFS filesystems from Linux.
IX.b / Filesystems

Filesystems and Windows/Linux compatibility

A filesystem determines how files and directories are stored on a partition. Windows and Linux support different filesystems natively, so the choice matters when a partition must be shared.

  • NTFS: Windows' main filesystem; well supported for Linux read/write access.
  • FAT32: widely compatible, but individual files are limited to 4 GiB.
  • exFAT: useful for removable or shared storage and supports large files.
  • ext4: a common Linux filesystem; Windows does not natively provide normal ext4 access.

The EFI System Partition is normally FAT32, but it is a boot partition, not a general-purpose shared storage location. Do not use it for personal files.

IX.c / Boot

Choosing the default operating system

The default operating system is normally controlled by the UEFI boot order and the bootloader menu. With GRUB managing the system, Debian can normally provide the menu from which Windows can also be selected.

If you want to change the default GRUB entry, use KDE's bootloader settings where available or configure GRUB directly. Do not delete UEFI entries just to change the default operating system.

The firmware's one-time boot menu remains useful when you need to bypass GRUB and start Windows Boot Manager or another UEFI entry directly.

IX.d / Maintenance

Updates and maintenance

Keep both operating systems updated independently. Windows Update manages Windows, while Debian uses APT for Debian packages.

Updates can occasionally modify bootloader files, firmware settings or available UEFI entries. After major updates, verify that both operating systems still boot normally.

Keep the installation and recovery USB available. It is especially useful if a bootloader update or firmware change prevents normal startup.

IX.e / Windows

Windows considerations

Windows should normally be fully shut down before booting Debian when Linux needs to access shared or Windows-owned filesystems.

Avoid re-enabling Fast Startup if you regularly access Windows partitions from Debian. Keep the BitLocker recovery key available because firmware, bootloader and hardware changes can trigger BitLocker recovery.

Windows feature updates can also change the preferred UEFI boot entry. If the machine suddenly boots directly into Windows, check the UEFI boot order before assuming that Debian has been removed.

IX.f / Linux

Linux considerations

Keep Debian's system partitions managed by Debian. Do not allow Windows tools to format or modify Linux partitions simply because they appear as unknown filesystems.

Before changing partitions, bootloader configuration or the EFI System Partition, make sure important data is backed up and record the current working configuration.

Good dual-boot practice: Keep each operating system responsible for its own system files, use a dedicated shared filesystem for common data, fully shut down Windows before Linux filesystem access, and verify both systems after major updates.
XII / Troubleshooting

Troubleshooting

Dual-boot problems are usually easier to solve when the failure is isolated first. A system that does not boot, a system that boots but has no network, and a system that cannot install packages are different problems and should be diagnosed separately.

The general rule is: observe first, change second. Record the error message, identify the affected disk or device, check logs and configuration, and only then apply a repair.

Do not make multiple repairs at once. Changing the bootloader, partition table, firmware settings, and operating system configuration simultaneously makes it difficult to determine what actually fixed or caused the problem.

Useful first checks

From Debian, these commands provide a quick overview of the running system: 

uname -a
                cat /etc/os-release
                lsblk -f
                findmnt
                sudo efibootmgr -v
                ip addr
                ip route

For recent system and service failures, inspect the system journal: 

journalctl -b -p warning
                journalctl -b -p err

-b limits the output to the current boot and -p filters by message priority. These commands are often more useful than guessing which configuration file needs to be changed.

XII.a / Windows

Windows will not boot

First determine whether the problem is Windows itself or simply the boot path. Enter the firmware's one-time boot menu and look for Windows Boot Manager.

If Windows Boot Manager exists, select it directly. If Windows starts, the Windows installation is probably intact and the problem may be GRUB or the UEFI boot order.

Use Windows recovery

If Windows Boot Manager does not successfully start Windows, boot the Windows installation USB and select: Repair your computer → Troubleshoot → Advanced options.

Start with Startup Repair. If it cannot repair the system, open Command Prompt and inspect the disks: 

diskpart
                list disk
                list volume
                exit

Identify the Windows partition and EFI System Partition by their filesystem, size, and layout. Do not assume that Windows is C: inside recovery mode; drive letters can differ there.

After identifying the Windows partition, a filesystem check can be run with: 

chkdsk C: /f

Replace C: with the actual Windows volume letter in the recovery environment.

Rebuild UEFI Windows boot files

If the Windows installation is present but its UEFI boot files are damaged, assign a temporary letter to the EFI System Partition: 

diskpart
                list volume
                select volume N
                assign letter=S
                exit

Replace N with the EFI System Partition. Then rebuild the Windows boot files, using the correct Windows volume letter: 

bcdboot C:\Windows /s S: /f UEFI

Restart and check the firmware boot menu again. Do not format the EFI System Partition simply because Windows does not boot.

XII.b / Debian

Debian will not boot

First use the firmware boot menu to determine whether a Debian or GRUB UEFI entry is present. If Debian starts from the firmware menu but not from the normal boot order, the Debian installation may be fine and only the UEFI boot order needs attention.

Check GRUB

If GRUB appears but Debian fails to start, note the exact error. Common failures include an incorrect root filesystem, missing initramfs, filesystem errors, or a kernel problem.

If you can reach a shell, inspect the disks and mounts: 

lsblk -f
                findmnt /
                findmnt /boot
                findmnt /boot/efi

Check the previous boot for useful errors: 

journalctl -b -1 -p err

If Debian cannot boot at all, use the rescue USB and mount the installed system before attempting repairs. Avoid running repair commands against the wrong disk or an unmounted target filesystem.

XII.c / Bootloader

GRUB or bootloader problems

GRUB is the bootloader normally responsible for presenting the Debian boot menu and loading Debian. On a UEFI system, GRUB itself is stored as files on the EFI System Partition and is started through a UEFI firmware entry.

Check UEFI entries

sudo efibootmgr -v

Look for entries such as debian and Windows Boot Manager. Check the BootOrder before changing anything.

If Windows is present but missing from GRUB, first verify that Windows still boots directly from the firmware menu. Then, from Debian: 

sudo update-grub

This regenerates the GRUB menu configuration and normally detects Windows when the required Windows boot entry and detection support are available.

Reinstall GRUB when necessary

If GRUB itself is damaged but Debian's filesystem is intact, reinstalling the Debian GRUB packages and regenerating the configuration is usually preferable to manually recreating firmware entries. 

sudo apt install --reinstall grub-efi-amd64 grub-efi-amd64-bin
                sudo update-grub
Do not randomly delete UEFI entries. A missing GRUB menu, a missing firmware entry, and damaged boot files are different failures. Identify which layer is broken before repairing it.
XII.d / UEFI

UEFI and firmware problems

UEFI firmware sits below both operating systems. Incorrect firmware settings can therefore make a perfectly intact installation appear broken.

Check the important settings

  • Boot mode should be UEFI.
  • Legacy/CSM should normally remain disabled.
  • The internal SSD should be detected by the firmware.
  • Windows Boot Manager and/or Debian should appear as UEFI boot entries.
  • Secure Boot should be changed only when there is a specific reason.

If the firmware was reset after a BIOS update or CMOS reset, re-check these settings before changing anything inside either operating system.

Check from Debian

sudo efibootmgr -v

If this reports that EFI variables are unavailable, Debian may itself have been booted in Legacy mode rather than UEFI mode. 

test -d /sys/firmware/efi && echo "UEFI" || echo "Legacy"
Firmware updates: A motherboard firmware update can reset boot order or other settings. Record the working UEFI configuration before updating firmware and verify it again afterward.
XII.e / Storage

Disk or partition problems

Partition problems require extra caution because a wrong command can cause immediate data loss. Start by identifying the physical disk and inspecting it without modifying anything. 

lsblk -o NAME,SIZE,FSTYPE,FSVER,LABEL,UUID,MOUNTPOINTS
                sudo fdisk -l
                sudo blkid

Compare the output with the disk layout documented before installation. Pay particular attention to disk size, partition sizes, filesystem types, and the EFI System Partition.

Check a Linux filesystem

Filesystem checks should normally be performed while the filesystem is unmounted: 

sudo umount /dev/sdXN
                sudo fsck -f /dev/sdXN

Replace the device with the actual Linux partition. Never run fsck against the mounted root filesystem unless using an appropriate recovery procedure.

Check drive health

For drives supporting SMART, install and use smartmontools: 

sudo apt install smartmontools
                sudo smartctl -a /dev/sdX

NVMe devices can also be inspected with: 

sudo nvme list
                sudo nvme smart-log /dev/nvme0
Stop before partition changes. If partitions suddenly disappear, the disk reports I/O errors, or the filesystem appears corrupted, do not immediately recreate the partition table. Preserve the current state and consider making a forensic or sector-level backup first.
XII.f / Network

Network/Wi-Fi not working

Separate a hardware-detection problem from a network-configuration problem. First determine whether Linux can see the network adapter: 

ip link
                lspci -nnk | grep -A3 -i network
                rfkill list

If Wi-Fi is blocked, check whether it is a software or hardware block: 

sudo rfkill unblock all

If the adapter appears in lspci but has no driver, inspect the Kernel driver in use and firmware messages: 

sudo dmesg | grep -iE 'firmware|wifi|wlan|network'

Debian firmware packages are commonly required for wireless adapters. Make sure the non-free-firmware repository is enabled before installing the appropriate firmware package.

Check the connection

ip addr
                ip route
                ping -c 4 1.1.1.1
                ping -c 4 debian.org

If the IP address test works but the domain test fails, the problem is likely DNS rather than the physical network connection.

XII.g / Audio

Audio not working

Modern Debian desktops normally use PipeWire and WirePlumber for desktop audio. Start by checking that the audio hardware is detected: 

lspci | grep -i audio
                wpctl status

wpctl status shows PipeWire's detected devices, sinks and sources. Check that the expected output device is available and not muted. 

wpctl get-volume @DEFAULT_AUDIO_SINK@
                wpctl set-mute @DEFAULT_AUDIO_SINK@ 0

If the device is detected but audio services are malfunctioning, restart the user audio services: 

systemctl --user restart pipewire pipewire-pulse wireplumber

Also check KDE's audio settings and verify that the correct output profile is selected, particularly when HDMI, DisplayPort, Bluetooth, and onboard audio are all available.

XII.h / Graphics

Display and screen problems

First determine which graphics hardware is present: 

lspci -nnk | grep -A3 -E 'VGA|3D|Display'

The output shows the graphics controller and, when available, the kernel driver currently handling it.

Check displays

kscreen-doctor -o

KDE's display configuration can also be opened from System Settings → Display & Monitor. Check resolution, refresh rate, scaling, and whether the correct monitor is enabled.

Check graphics errors

journalctl -b | grep -iE 'drm|gpu|amdgpu|i915|nouveau|nvidia'

Common causes include a missing firmware package, an incorrect graphics driver, unsupported kernel parameters, or a display connected to a GPU output that is not currently active.

Do not install random graphics drivers. Identify the GPU first. Debian's recommended driver and firmware path depends on the hardware and whether the system uses integrated, AMD, Intel, or NVIDIA graphics.
XII.i / Packages

Package installation and broken-package problems

When APT reports dependency or configuration errors, do not immediately remove packages at random. First determine whether the package database or an interrupted configuration operation is responsible.

Refresh and finish pending configuration

sudo apt update
                sudo dpkg --configure -a

If dependencies are incomplete, ask APT to repair them: 

sudo apt --fix-broken install

Then retry the normal upgrade: 

sudo apt full-upgrade

Inspect a package

apt policy package-name
                apt show package-name
                dpkg -l package-name

apt policy shows available versions and repository priorities, while dpkg -l shows the package's installed state.

Do not mix repositories casually. Debian Stable, Backports, Testing, and Unstable packages are not interchangeable. A dependency problem caused by mixed releases can be considerably harder to repair than the original missing package.
XII.j / Users

User, permissions, and sudo problems

Linux permissions determine which users and groups may access files and resources. When something fails with Permission denied, first inspect ownership and permissions rather than using chmod 777. 

id
                groups
                ls -l /path/to/file
                ls -ld /path/to/directory

Check whether the user has administrative access through sudo: 

sudo -v

If sudo reports that the user is not allowed to run commands, verify group membership: 

groups

On a normal Debian desktop, administrative access is commonly provided through the sudo group. Group membership changes may require logging out and back in before they are reflected in the session.

Repairing ownership

If a user's own files were accidentally created as root, ownership can be corrected carefully: 

sudo chown -R "$USER:$USER" /path/to/directory
Be careful with recursive commands. Never run chown -R or broad chmod -R against /, /usr, or other system directories unless you have a specific recovery procedure and understand the consequences.
XII.k / Recovery

Using the rescue USB

The Ventoy USB is a recovery tool as well as an installation device. Debian installer media, SystemRescue, GParted Live, and other utilities can be used when the installed operating systems cannot boot.

Identify the disks first

Boot SystemRescue or another suitable Linux environment and inspect the storage devices: 

lsblk -o NAME,SIZE,FSTYPE,LABEL,UUID,MOUNTPOINTS
                sudo fdisk -l

Identify the target disk by capacity and partition layout. Device names such as /dev/sda and /dev/nvme0n1 are examples; they are not guaranteed to remain the same across boots.

Mount a Debian installation

If the installed Debian root filesystem is intact but cannot boot, mount it under a temporary directory and inspect its configuration: 

sudo mount /dev/ROOT_PARTITION /mnt
                sudo mount /dev/EFI_PARTITION /mnt/boot/efi

If the system has a separate /boot partition, mount that at /mnt/boot as well. The actual partition names must be identified from lsblk; never copy the example names blindly.

Use the rescue environment for diagnosis first

Inspect logs, filesystem state, partition layout, and boot files before making changes. The rescue environment is particularly useful when the installed system cannot provide a working shell.

Recovery rule: Do not format, repartition, or recreate an EFI System Partition simply because an operating system fails to boot. In a dual-boot system, the existing EFI partition may contain boot files for both Windows and Debian. Preserve it until the failure has been identified.
Good troubleshooting practice: Identify the failing layer first: firmware, UEFI entry, EFI files, GRUB, kernel/initramfs, filesystem, network, graphics, audio, or userspace. Repair only that layer when possible, then reboot and verify the result.
